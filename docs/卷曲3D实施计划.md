# 卷曲 3D 实施计划（移植版，2026-11-16）

> **这一版把「自己发明几何」整条否掉，改成照搬成熟实现。**
>
> 上一版（2026-11-15）是我自己推的圆柱模型：整页在折痕处对折，掀起的部分绕过半圈后
> **平铺到另一侧**、盖住当前页，再叠三层沿整条折痕铺满的透明覆盖（纸背压淡、纸卷明暗、落影）。
> 真机上的结果读者读不出来 —— 只见半透明滚轴加几条深浅不一的长条，分不清哪张是纸、
> 哪面是反面。**几何不是「调参不到位」，是模型选错了。**

## 目标

翻页时纸**卷起来**：手指在哪，卷轴就在哪；卷轴一侧的纸被卷进卷筒、其余不画；
新页从卷轴另一侧露出来。读者一眼能认出「这是一张纸在卷」，不需要任何说明。

## 参考实现（照搬，不发明）

| 来源 | 位置 | 搬什么 |
| --- | --- | --- |
| moon+ | `samples/moon/sources/com/flyersoft/views/NewCurl3D.java` | `Mesh3D.curl(...)` 的扫线网格、顶点色明暗、两种影、画序 |
| 多看 | `samples/duokan/sources/fi/harism/curl/CurlMesh.java` | 交叉核对卷筒参数化（同一套圆柱数学） |

**moon+ 的关键结构**（也是我上一版缺的）：

1. 把页面四角**旋转到手指方向**的局部坐标系（`rotateZ(-acos(dir.x))`，平移到手指点），
   于是卷轴永远是「竖直的」——不需要为斜折痕单独写几何。
2. 沿卷轴扫线：`0 → −πR` 分 `mMaxCurlSplits` 段，最后再加一条「纸的另一条边」。
   每条扫线对应一个圈角 θ，屏幕位置是 `R·sin θ` 一类的正向映射。
3. **卷轴之后的纸不画**（不是折回另一侧）。所以画面只有：当前页（平）+ 卷筒 + 新页（平）。
4. 顶点色就是明暗（`mColors`），纸背与正面用不同的明暗系数；影是**独立的两套顶点**
   （投在下面那页上的落影、卷面自阴影），一起送进 GL。
5. 画序：落影 → 纸背 → 正面，全部由渲染器按固定顺序出。

## 原则（不变）

1. 纹理供给不动：页栅格 + 覆盖层两张图，`CurlPageImages` 收。**唯一例外是交给网格前的那一次合成**：
   覆盖层是透明底的整页图，卷曲的网格路径（`drawVertices`）在桌面端会把透明像素抬成顶点色（白），
   整张卷起来的纸因此被刷白、只剩旁注（读者原话「反面没有文字，只有批注」）。所以有覆盖层时先把
   页栅格与覆盖层烤成**一张不透明整页图**（平板口径约 20MB，翻页结束即丢），再交给网格，
   顺带每帧少一遍贴图。不新建常驻图池。
2. 纸背 = 同一张纸的背面，读者写的字透过来、页码也一样。
3. 几何在 CPU 铺点，光栅/采样/插值在 GPU。
4. **不再有任何「自己发明」的系数**：半径、扫线段数、明暗系数全部取自参考实现，
   要改必须有对照图为证。唯一的例外是半径封顶 10% 页宽（参考值的 ≈0.108 页宽会把新页的
   正文咬掉，见「当前状态」第 3 条），对照图就是平板尺寸下的 `dev-fwd-p*.png` 两组。

## 落地方式（已经跑通的那一段不再动）

纹理与明暗的**绘制手段**已验证可用，保持：

- 纹理：Compose 公共 API `Vertices` + `ImageShader` + `Canvas.drawVertices`
  （跨平台、无平台分叉、无版本门槛；顶点色必须与顶点数等长，传白色 + `SrcOver`）。
- 明暗：几何自带顶点色不可靠（真机随机色），**明暗改为与几何同源的一维渐变**：
  扫线的 θ 是单调的，明暗是 θ 的函数 ⇒ 一条多段渐变精确表达，不需要顶点级着色。

## 步骤

### P1 移植网格（核心，先出图）—— 已完成

- 新建 `curl/CurlMesh.kt`：按 `Mesh3D.curl` 逐行移植，输入 = 手指点 + 方向 + 半径，

  卷筒位置、卷筒宽度、纸背可见范围、新页起点。

- 两道影照抄：落影（卷筒投在下面那页）+ 自阴影（卷筒靠折痕一侧）。
- 验收：卷筒在图上是一个**有暗边的圆筒**，而不是一条均匀亮带。

### P3 去掉多余覆盖 —— 已完成

- 删掉上一版的三条沿整页铺开的透明覆盖（纸背压淡 / 明暗带 / 第二道影）：
  它们就是读者看到的「深浅不一的长条」。
- 纸背压淡只在纸背那一小段上画，不跨整页。

### P4 接回翻页层 —— 已完成

- `USE_CURL3D` 打开，3D 优先、退化才退回折页。
- 等图规则、末帧扶正、松手收尾全部沿用。
- **书脊恒在左**：翻页层不按翻页方向镜像几何。上一页走同一套「左边平铺、纸卷朝右」的
  几何的 `1-p`，折痕斜率原样带过去（几何层不取反，两个方向同一根折痕），并把被翻的那张纸
  换成上一页（目标页）——镜像会让纸挂在右缘、看起来右边成了书脊（见 `docs/翻页动画设计.md` §17.5）。
  手势斜率按 `leanOf` 算：左半边（折痕锚点）「折痕垂直于手指轨迹」，右半边（页边锚点）
  两个翻页方向同向、以翻下页为准（读者 2026-11-26：「右侧翻上页时，在同一个位置，与右侧
  翻下页的动作方向完全不同，以翻下页的动作方向为准」）。两种锚点的拖动方向都从**按下点**
  量起，横向分母锁在**外向行程的最大值**上，越过按下点后不换号、往回收也不转正——直接按
  此刻的 `u_x` 取符号会在越过按下点时整根镜像，按此刻的 `|u_x|` 取大小则收回时折痕会转成
  竖直；页边锚点拿页右缘当起点还会让翻上一页（手指向右）算反方向。

### P5 验收 —— 桌面已验，待读者在真机上翻一次

- 桌面：前/后两个方向各 4 档进度 + 斜折痕一档，逐张对形状（卷筒在掀起侧、新页在另一侧、
  九成时新页占屏幕大半、斜拖时页面四角仍是直角）。
- 真机：读者拖动确认手感；必要时录屏抽帧，不靠随手截图。
- 判据：① 卷筒是圆筒不是长条；② 纸背能看出是「同一页的背面」；③ 新页起点与手指一致；
  ④ 末帧逐像素等于目标页；⑤ 帧预算与折页持平；⑥ 翻上一页时书脊仍在左侧，不会换成右缘。

## 当前状态

- `USE_CURL3D = true`：3D 卷曲是默认的翻页动画，网格退化（折痕已在页面外）时才退回折页。
- 几何、纹理、明暗、落影全部按上面「落地方式」那一节实现，逐行照搬参考实现；
  自编的那套（半平面对折、半径跟进度、折痕回收、透视除法、顶点色）已整体删除。
- 与参考实现有意不同、且不再改回去的四处：
  1. **网格只铺掀起的材料那一半**（参考实现把平铺侧也铺进网格），平铺侧由整页绘制负责；
  2. 明暗用渐变叠白实现，不用顶点色（真机顶点色不可靠，且 8 位渐变表达不了大于 1 的乘数）；
  3. **半径封顶取 10% 页宽**（接近参考实现按手指压力算出来的 ≈0.108）。早先试过 3% / 5%，
     读者报「筒太细、折页反面根本看不出来」—— 筒细到一定程度，掀起的纸被压进几十像素，
     纸背只剩一条白边。10% 的代价是筒会盖住露出页靠折痕的那一条（宽度 = 半径），
     翻到一半约 0.03 页宽压在行首上，属于读者接受的取舍。
     半径的「剩余纸宽」夹取也已退役：收尾靠纸卷整根滚出页边，不靠把筒压扁（见 §17.2）。
  4. **半径还有一条「纸背至少占三成」的上限**（`R ≤ 掀起长度 × 0.7 / π`，参考实现没有）：
     纸卷绕半圈要吃掉 `πR` 的纸，半径超过「掀起长度 / π」时翻起来的那部分整段在筒上、
     一段平铺的纸背都没有，读者看到旧页的字被切断、切断处空无一物（原话「滚筒左侧的
     页面反面呢？为什么不画？」）。0.7 是「筒一眼看得见」与「纸背从起手就有」的交点：
     更小筒又细回去，1.0 则起手那段纸背的轮廓、落影、明暗全都不存在。
- 纸背不能只靠落影（`CURL3D_BACK_SHADOW_*`）：它与旧页同纸同色，一道影只能说明「这里
  有东西」，说明不了「这是一张纸」。纸背的可辨识度只靠**自己的镜像内容 + 折角两条直角边
  的接触影**。**不描边、不压暗**：描一条边、铺一层明暗，读者看到的分别是「卷筒左侧凭空
  多出一条痕迹」和「反面整体比正面暗」，两样都已退役。
- 目前**没有「筒内侧缝影」**：早先在筒内壁画过一层按折痕法向的渐变，但它与沿页边的接触影
  互不交融（读者判「三条影各画各的」），卷起来那截还会在筒左侧压出一道硬边（判「平白一条折痕」），
  已整体退役。筒身只靠「往白里压」的反光站立，暗面一概不画。
- 纸背的影是**沿页边走的接触影**（`CURL3D_BACK_SHADOW_*`，满宽 1.0R、浓度 0.62×落影）：
  `pageEdges` 给出两条页边（折痕端 → 最远纸角，跨全部扫线行：卷起来那截是弧、平铺段是直线），
  宽度从纸角满宽**匀速**收到折痕端 0，整体宽度从**纸背刚露头那一刻**渐入（页角处的纸在筒顶
  从正面朝上翻成背面朝上，弧长 πR/2；到平铺段出现的 πR 正好半宽，再走一个 πR 满宽）——
  零点早先在 πR，影要等纸角跨过卷筒左边缘才看得见，读者判「太晚了」；与折痕平行的自由边挨着纸卷，
  那里是纸自己压着纸，不落影。
  影带**只铺页边朝外那一侧**，纸背那一侧压根不画：早先两侧都铺、靠后画的纸盖掉内侧，可影一旦
  挪到纸之后（不挪就会被卷筒盖住），盖不掉的内侧半条就让纸背右边凭空多出一条灰带。
  朝外**由材料坐标定**，不投票：每一行落在哪条材料边上由 `texCoords` 给出（左/右/上/下），
  把它的外法向经网格的映射投到屏幕上（`J·m = n·off'(x')·(m·n) + t·(m·t)`）就是「背离纸面」
  那一侧。2026-11-26 之前是在平铺纸背那一段投票：纸角附近两条页边在屏幕上挤成一点、弦长
  全是噪声，右下角折起时票数为零、符号取默认值，整条右侧竖页边的影翻到纸上，再拖又翻回去。
  影带**画在所有纸段之后**：卷起来那截的朝外一片正好被圆柱远侧的纸投在身上，画在纸之前就会被
  盖掉，读者判「阴影被卷筒截断」。
  两条页边**各铺一条独立带子**（不拼成折返折线，那会在纸角自交、被 NonZero 抵消出缺口），
  纸角外两段带子端头之间那一楔由 `drawCornerFan` 补上，层数与浓度跟带子一致，拼起来是一整片，
  也不会在角上叠浓。扇形只在自由边退化成一点（两条直角边共用一个纸角）时才画。
- **纹理只画在版心材料范围内**（`textureStrip`），纸色只垫版心之外那两截（`marginStrips`）。
  > **2026-11-26 已废弃**：贴图改成整页、纸只有一种材料，`marginStrips` / `materialRect` /
  > `bleedEdges` 全部删除（来龙去脉见 `翻页动画设计.md` §17.6）。下面这一段是当时的原因。
  页栅格只有版心那么大（1585×2400 放在 1840×2800 里），页边距里没有像素：越界采样时
  `Clamp` 会拿版心最边一列去补，把那一列上的墨点拉成横贯页边距的短线（读者报
  「反面页边距上有好几条短横线」）；`Decal` 在这个后端的 `drawVertices` +
  `ImageShader` 下画出来是**不透明白带**，同样不能用。材料坐标沿扫线是线性的，所以「裁到版心
  矩形」以后还是四边形条带 —— 纸背的页边距因此仍是纸，纸卷卷进页边距的一截也只是纸，
  既不抹条纹，也不透出底下那页的字。
  **纸色不能整段铺**：整段先垫纸色再铺纹理，两层各自抗锯齿，交界那一列拿到「半列纸色 +
  半列纹理」，比两侧都亮，读者看到折痕上一条亮缝（「卷筒与纸正面交界处有一条多余的接缝线；
  背面也有」）。纸色按材料坐标只补版心之外，边永远压在纸上而不是纹理上。
  **露出页那一块同理**：它的四边形最后一条边就是折痕，整块铺纸色时纸色边正好压在折痕上、
  与网格第一行的半覆盖叠成一条亮线；改成四条边各按轴对齐矩形裁着铺（露出页是平的，屏幕
  矩形就等于材料矩形），版心留给纹理自己。
  **只收纸色还不够**：页图与覆盖层也从折痕起笔，抗锯齿的半列照样压在折痕上 —— 露出页在
  折痕附近是纸色时（新页栅格没就绪那一帧、折痕扫过页边距那几行）就成了一条与折痕平行的浅缝，
  深色页面上看着白、浅色页面上看着灰。所以露出页贴折痕那条边**整个多边形往里收一像素**，
  折痕那一列归翻走的那一页（背面 `drawPage` 已整页铺过、网格第一行再盖一次）。
  裁剪要**同时看材料 x 和材料 y**：折痕一斜，一条扫线横跨的材料 x 能差大半个页宽，只看行首
  的 x 会把越界那半行也画进来，于是竖着翻没事、往页角斜着掀时页边距上冒出几条短横线。
- 两处只有对着出图才会发现、已经改过来的口径：
  - **卷曲量到屏幕偏移要取负**。接反时纸卷鼓向没掀起的那半页、平铺段盖住
    露出页，翻到九成屏幕上仍是大半张旧页、同一段文字叠两三处。
  - **半径不能按进度算**：进度 0.2 时半径 0.2 页、掀起的材料也正好 0.2 页，纸一离开折痕
    就绕满 1 弧度，「翻了两成」看起来几乎没动。按「剩下的纸」算才对。
  - **筒径整段不变**：`R = min(10% 页宽, 折痕到还没掀起那一侧页边的距离)`。早先为了「纸背
    从第一下拖动就在」，额外把筒径压到 `掀起长度 × 0.7 / π` —— 筒径因此十倍变化，读者判
    「有时候直径会变化，有时候被压扁」。这条已退役：**筒径不变优先**，代价是掀起长度不足
    `πR`（进度 0.31 之前）时没有平铺的纸背，只有筒和纸边。
- 剩余的已知差异（不影响使用，暂不处理）：参考实现那道「自阴影」（整条卷面按法向压暗）这里
  没有对应实现 —— 只有「往白里压」的反光，筒内侧那层缝影已退役；落影的衰减用的是线性渐变，
  参考实现是沿网格顶点的 penumbra 插值。
- 落影的**形状**是贴着纸卷轮廓的一条带（把轮廓逐段沿法向挤出影宽）：内侧边界必须就是纸卷的边。
  三条错法都踩过：按折痕铺贯满整页的平行四边形（影跑到圆弧外面）、拿与折痕平行的直线当内侧
  边界（纸边在两端是弯的，直线与弯边之间裂出一条没影的窄带）、只取轮廓外面一段扫线（离边还差
  一截就断）。纸被页边切断处影跟着到页边，纸自己收边处影跟着纸边转弯。

## 跟手的开销与折痕抖动（2026-11-17）

读者的反馈是「跟手的时候有卡顿，手指滑动时卷起的页边有点抖动」——问题不在松手后的结算动画，
在**拖动中每一帧**。两条独立的病根：

### 一、一帧的绘制开销

真机实测（平板 PA2353，无仪器探针的粗测）：拖动期间 CPU 每帧中位数 38ms、九成 121ms、
过半帧超过一帧预算；GPU 只有 5ms。所以瓶颈在**主线程录制绘制指令**，不在填率。
逐段探针把开销定位在纸段网格与落影上，其余（提笔几何、卷筒明暗）都是零点几毫秒。

改法都是「把每帧新造的东西变成复用或视图」，画面本身不动：

1. **纸段按三角带画**。网格本来就是「每行两个顶点、相邻两行连成四边形」，段内顶点在数组里
   连续（`firstRow*2 .. lastRow*2+1`），正好是一条三角带 —— 不再需要每帧把索引摊成
   两千多个装箱整数的列表。顶点坐标与纹理坐标用数组视图直接喂给绘制，
   也不再摊成两份 `List<Offset>`（一帧几千个临时对象）。
2. **纹理画笔按图缓存**。`ImageShader` 只跟图有关、跟几何无关，一页栅格只建一次画笔；
   早先是每段纸、每帧各建一个。
3. **落影折线抽稀 + 路径复用**。影是软的，页边几十行的细节在屏幕上看不出来：折线抽到
   24 个点，十六层影共用同一个路径对象（每层 reset 后重填），不再每帧新造几十个 `Path`。
   影的层数、浓度、宽度口径一律不变。

验收：同一组进度（0.15/0.30/0.45/0.55/0.70/0.85，倾斜 0.3）改前改后逐像素对比，
差异只在纸段接缝与影带边缘的几行抗锯齿上（≤0.12% 像素、单通道最大 21/255），肉眼无差。

真机同一位置、同一组手势（三次前翻 + 三次后翻，各量三轮，取三轮范围）：

| | 帧耗时中位数 | 九成 | 掉帧比例 | 丢 vsync |
|---|---|---|---|---|
| 改前 | 26–38ms | 65–113ms | 27–53% | 7–20 |
| 改后 | 16–19ms | 42–53ms | 16–22% | 2–6 |

逐段探针的落点同向：纸段一段从 2.5–14.6ms 降到 1.1–2.4ms，落影从 1.7–10.7ms 降到
0.4–1.7ms。注意两份数都要在装完包、跑热之后取：刚装完的头几轮是被 JIT 和首翻冷路径
拖慢的（同一支包能出现 36ms 的读数），拿它当基线会把正确实现测成没改善。

### 二、卷起的页边抖动（折痕倾斜）

倾斜乘的是 `0.9 × 页宽` 的外扩幅度：平板上**一个单位倾斜 ≈ 1656px 的折痕端点位移**。
而倾斜原来的取法 `dy / hypot(dx, dy)` 是手指位移的瞬时方向 —— 横划时手指上下自然抖动几像素，
倾斜就跳 0.02～0.05，折痕两端跟着来回摆几十像素，卷起来的页边因此抖。起手最初几十像素更糟：
`dx` 接近 0，方向角几乎全是噪声，能一下把倾斜推到 ±1（折痕几乎躺平）。

改法（`FlipController.updateCurlTilt`）：

- **指数滑动平均**：每个指针事件朝目标值走 0.22（60–120Hz 采样下时间常数约 30–60ms）。
  「拖动方向」是慢变量、手指抖动是快变量，低通只压抖动，跟手仍即时。
- **起手门槛**：位移不足 24px 时不动倾斜（保持 0、折痕竖直），走出这段再跟手。

倾斜的语义、外扩幅度、松手后保持（结算期间形状不跳变）都没变；末段扶正照旧。

> 后续（见 `docs/翻页动画设计.md` §16.6）：平滑与门槛已随「折痕 ⟂ 拖动方向 + 抓点锚定」
> 一起退役——拖动方向本身就是位移积分、天然平滑，低通反而是斜拖跟不上的原因。
> 这里保留当时的过程记录。`FlipController.updateCurlTilt` 现名 `updateCurlPull`。

### 三、折痕一斜就掉到 20fps（包围盒填充）

上一条改完仍有「斜着划更抖」的直觉，探针一量坐实了：**折痕倾斜为 0 时一帧 16.5ms，
倾斜不为 0 就 48–64ms**，与手势快慢无关，只跟折痕斜不斜有关（合成手势：直线滑 16.5ms，
带 300px 上下位移的斜滑 50ms 上下，与真手指一致）。

逐段探针把多出来的四十来毫秒锁在两处**非矩形裁剪路径**和**页边影带**上：

1. 折痕一斜，纸段纹理与露出页原来的 `clipPath` 裁切路径就不是矩形。抗锯齿裁切会让 Skia
   为它开一张整页大小的图层，一帧多三十来毫秒。改成把裁切做进**几何**里：露出页按
   `clipPolygonToRect` 裁形状后用 `ImageShader` 填路径；纸段纹理用 `textureStrip`
   按行把材料范围裁进三角带的顶点里，`ImageShader` 走 `Clamp` 兜底。
2. 页边那道柔和的影原来是**十六层薄填**叠出来的渐隐。路径填充按**包围盒**栅格化，
   而影带又长又细、斜着横过页面，整条的包围盒能撑到大半页：十六层 × 两条边就是十几页的
   填充量。先试过把带子切成几段（每段包围盒贴自己那段）能把 50ms 压到 36ms，但每段仍是
   一次路径填充、还多出几百次 draw call，治不干净。

最终改法：**影带改成一条三角带一次画完**，浓度沿宽度方向的剖线烘进一张一维纹理
（数值就是原来十六层叠色的解析解），顶点纹理坐标的 `v` 就是「离纸边的归一化距离」。
顶点色仍全白（安卓上可变顶点色不可靠），浓度靠 `Paint.alpha` 乘。
三角带没有抗锯齿边，最内侧压进纸里半像素、浓度取一半，与外侧满浓的半像素叠出抗锯齿过渡。

验收（同一帧、同一组进度与倾斜，与逐层版逐像素对比）：差异集中在影带内部的台阶
（原来十六级台阶，现在台阶之间线性过渡）与纸边那一行抗锯齿，超过 6/255 的像素占 0.1%，
单通道最大 42/255，肉眼无差。真机斜滑的中位帧耗时从 53–59ms 降到 18ms（直线滑 16.7ms），
斜着划与直线划不再有区别。

### 四、影的观感定稿：页边那条影退回十六层叠色

上面第 2 条（影带改三角带 + 剖线纹理）虽然把数值取成十六层叠色的解析解，实际上屏一对比，
读者还是看出来了：**纹理里那 256 行是「平台 + 硬台阶」，而十六层路径填充的台阶边界各自带
抗锯齿**，两层一叠，观感并不一样。读者先判「一段段」，随后又判「阴影还画在页边上」——
那条影最终整体退回十六层叠色。

现在两件事分开：

- **影保持原样**：十六层路径填充、纸角那块扇形、最内侧半像素的抗锯齿 apron、逐行采样的页边
  （不抽稀——抽稀后影的内沿变成一段段弦，会从纸边上啃出三角缺口），每帧只共用同一个路径对象。
- **性能只拿裁剪那一半**：露出页与纸段纹理改走几何裁切（见上），这才是斜划掉到 20fps 的大头
  （一帧三十来毫秒）；影带那部分（包围盒填充）原样保留，代价是斜划比直线滑仍多几毫秒。

验收（同一组进度与倾斜，与退回前的版本逐像素对比，平板上 JVM 渲染）：倾斜为 0 的帧
**完全一致**（最大差 0）；倾斜 0.3 的帧差异只在折痕那条线上（新页形状的抗锯齿，0.02% 像素
超过 1/255、单通道最大 20/255），页边影带区域**零差异**。

### 五、跟手又抖了：每帧重烤一张整页图（2026-11-20）

读者反馈「跟手翻页又有点抖动」。这次画法本身没变，问题出在**缓存判据**：

1. 卷曲网格要一张**不透明整页**贴图，有旁注/页码时由页栅格 + 覆盖层现场合成一张
   （`CurlPageBake`，平板口径 1840×2800 ≈ 20MB），按「页栅格这一版 + 覆盖层这一版」缓存，
   只服务本次翻页。
2. 判据是 `RasterTexture.equals`，它按位图的**实例**认「同一版像素」；纹理画笔缓存
   （`CurlTextureCache`）同样按实例。
3. 安卓平台每次取页图都调 `Bitmap.asImageBitmap()`，而它**每次新建一个包装对象**
   （`AndroidImageBitmap`，反编译确认：`new` 之后直接返回，没有任何缓存）。页槽又是逐帧
   绘制的 ⇒ 每帧一个新包装 ⇒ 两处缓存逐帧判废：**每帧重新合成一张整页图（≈20ms）+
   每帧重建纹理画笔**，外加每帧 20MB 分配带来的 GC。

真机实测（PA2353，合成手势 700–800ms 横划/斜划，`Orilumn.Curl perf`）：

| | frames | avg | p50 | p90 | 每场 bake | paint |
|---|---|---|---|---|---|---|
| 改前 | 13–19 | 32–59ms | 32–60ms | 42–72ms | =帧数（12/16/18） | ≈2/帧 |
| 改后 | 34–129 | 5.1–7.3ms | 5.5–7.2ms | 6.0–8.2ms | 1（偶有 3，见下） | 3 |

（都取装完包跑热之后的轮次；刚起来头一两轮仍受 JIT 影响，p50 二十几毫秒，与第 208 行同一个坑。）

改法：**同一张平台位图的 Compose 包装只建一次**（弱键表，键是位图本身；
`PageRasterStore` 淘汰并 recycle 后条目自行消失）。没有改任何绘制逻辑，像素逐帧不变；
缓存判据恢复成它本来想表达的意思。

> `bake` 偶尔不是 1：目标页的页栅格在翻页途中才真正就绪（换了新位图）或覆盖层重画过（换了
> 内容代数）时会再合成一次，那是对的——**判据看的是「这一版像素」**，不是「永远是同一张」。
> 判废的标准仍只有一条：`bake ≈ frames`。

顺带定下一件可长期用的东西：每次卷曲翻页结束落一行 `Orilumn.Curl perf`（帧数、平均/中位/
九成耗时、整页合成与纹理重建次数，见 `docs/调试日志与分页跟踪.md` §4.1.1）。以后「感觉又抖了」
先看这一行：`bake` 等于帧数就是本条复发，`p90` 超过 16ms 才是真的掉帧。

还剩一处已知的一次性开销：**每场翻页第一帧要合成那张整页图**（≈20ms）。它落在起手后的
第一帧上，晚一帧出画；因为只发生一次且页边距里没有像素可省，暂不处理。
