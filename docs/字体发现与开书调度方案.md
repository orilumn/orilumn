## 1. 证据（现状 → 为什么必须改）

### 1.1 一次扫描的实测成本

20:22 那次开书现场 `jstack`：

```
"DefaultDispatcher-worker-1" cpu=88431ms RUNNABLE
  FontMgrKt._nMatchFamily
    ← NameTableChineseNames.chineseOf / scanAll
      ← DesktopReaderHost.syncPanelFonts (DesktopReaderHost.kt:271)
```

一次 `syncPanelFonts()` 里叠了**两趟逐族 `matchFamily`**：

1. `systemFontFaces()`（`SystemFonts.kt`）逐族展开 `FontStyleSet` 取字重名；
2. `NameTableChineseNames.scanAll()`（`NameTableChineseNames.kt:40`）再逐族 `matchFamily` +
   读 `name` 表（大 CJK 字体几十 MB）。

本机存储（`~/.orilumn/orilumn.db` 的 `font_faces` 表）现为 **442 个系统族 / 8892 条字形行**
（`source='system'`），即两趟逐族 `matchFamily` 要跑 ~442 次，再叠 `name` 表读取，
单线程烧到 **88 秒**量级。

### 1.2 它撞的是谁：第 1 档锚页排版

`open()` 之后锚页排版同步塑形（第 1 档，`PRIO_FLIP=0`，不进队列），而扫描在原生
**FontMgr 锁**上跑——两者同一把锁、同一批核。日志表现：**断在 `chapter loaded`、
CPU 8.3%**（在等锁，不是在算）。即扫描把第 1 档的目标页排版挤成了"排队等锁"。

健康对照（同一本书、同章、无并发扫描）：锚页 `LARGE-ANCHOR` 落位
`14:35 = 1348ms / 18:26 = 1453ms / 19:23 = 1496ms`。

### 1.3 为什么它总在开书跑

```kotlin
// ReaderView.kt:253-256
// 面板字库经宿主装载（R4：枚举+中文名链已下沉 syncPanelFonts，视图只收表；…）
LaunchedEffect(book) {
    fontEntries = desktopHost?.syncPanelFonts() ?: fontLibrary.allEntries(fontLibrary.list())
}
```

键只跟 `book` ⇒ **每开一本新书跑一次**。进程内有 `chineseNames` 缓存（`NameTableChineseNames.kt:27`），
只有本进程第一次真扫；但每次重启进程又从零开始。

**平板同构**（同一缺陷、另一份代码）：

```kotlin
// ReaderActivity.kt:238-243（openBookEngine 内，开书路径）
runCatching {
    fontRepository.syncSystemFaces(
        orilumn.reader.engine.skia.systemFontFaces(),
        fontRepository.systemFontLocalizedNames(),
    )
}
```

平板的本地化名走 `FontParser` name 表直读（无 CoreText 桥），且 `loadPanelFonts`
（`ReaderActivity.kt:496-501`）**在开面板时也会重枚举一次**——即平板其实已经"面板需求模式"在跑，
只是**开书那一拍也多扫了一趟**（F4c）。两端同症：把扫描从**开书**搬到**面板可见 / 启动检测**即可。

### 1.4 「序列化存储」其实已经有了

`syncPanelFonts` 最终落 `fontLibrary.syncSystemFaces(sys, localizedNames)`
（`DesktopReaderHost.kt:275` → `LibraryDb.syncSystemFonts`），系统行 + `displayName` 已写进
**全应用范围**的 `fonts` 表（跨书、跨进程）。核实：本机 `font_faces` 现为
**442 族 / 8892 行，`source` 全为 `system`**——序列化存储已就位。

⇒ 缺的不是存储，缺的是**「何时才值得重扫」的判据**与**调度**。

### 1.5 说明：6.46s 那个尖峰**不是回归**

同一本书同章其它时刻 1.35–1.50s；18:26 那次同样并发 `ch=0` 重排，锚页仍 1.45s。
20:28 那次进程 `ps lstart`=20:28:30（开书前 6s 冷启），4 核，两个 Gradle daemon，loadavg ~3。
⇒ 冷启动 JIT + 冷字体名缓存的环境量，不是代码回归。**本方案不针对它**。

## 2. 字体发现三层次设计

### 2.1 层次一：全系统扫描 → 扫一次、序列化、不随开书走

**扫描体（从低到高）**

| 段 | 调用 | 成本 |
| --- | --- | --- |
| ① 族名枚举 | `systemFontFamilies()`（`familiesCount`+`getFamilyName`） | **廉价** |
| ② 字形枚举 | `systemFontFaces()`（逐族 `FontStyleSet`） | **贵**（一趟 `matchFamily`/族） |
| ③ 本地化族名 | 桌面 `NameTableChineseNames`（方案B）+ `MacFamilyNames`（方案A，CoreText） | **最贵** |

**序列化目标**：直接复用现有 `fonts` 表（全应用范围、跨书、跨进程），**不新增第二份存储**；
只补一个**指纹**用于判废。

**指纹** = `(cacheSchemaVersion, hash(sorted(systemFontFamilies())))`。

- 族名集合不变 ⇒ 认定未变，**跳过 ②③**，`displayName` 直接从库里读。
- `cacheSchemaVersion` 用于本地化名推导逻辑变更时主动作废（不必等系统字体变）。

**读取方（字体面板）**只走 `fontLibrary.allEntries(fontLibrary.list())`（DB 直读，廉价），
**不触发扫描**。

### 2.2 层次二：阅读期变化检测 → 每次启动只检测一次（**进调度**）

1. app 启动后**一次性**跑 ①（廉价族名枚举）+ 比指纹（`@Volatile once` 门控）；
2. 指纹变 ⇒ 在档 **45** 提交一次**增量**重扫（补/删系统行 + 更新 `displayName`）；
3. 指纹不变 ⇒ **什么都不做**——这是常态，也是开书变快的根本。

> 「打开阅读应用后只检测一次」= 检测一次；**检测一次 ≠ 扫一次**。面板要就扫，见 2.4。

### 2.3 层次三：导入（本地 / Wi-Fi）→ 立即更新（**不进**调度）

用户直接动作、面板正开着，`importBytes` 后立即 `refreshFonts()` 即可（现状已如此，保留）。
导入为 `source='imported'`，与系统列表无交集，不触发层次二。

### 2.4 面板需求模式：**面板在用 = 池顶，立即实扫**

> 规则（本轮修正）：**面板要用的时候，优先级就很高了**——不能只显示"扫描中"占位，
> 要**立即实时扫描**；**除非用户关闭面板**。

因此字体扫描的优先级**不是常数，是面板可见性的函数**：

1. 面板打开 → 立即渲染 **DB 已有列表**（常态库热 ⇒ 瞬间全量，根本不扫）；
2. 若库冷 / 指纹过期 → 同键**提档到池顶（5）**，**真扫**；列表**随每族完成增量刷新**，
   并显示真实进度（已 N / 共 M 族）——这才叫"实时"，不是静止的"扫描中"；
3. 面板关闭 → 同键**降回 45**（或 `cancelKey`）；下次打开再提档续跑。

## 3. 调度落点

### 3.1 档位常量（新增两个，插空档、不重编号）

`TaskScheduler.Companion`（`TaskScheduler.kt:45-83`）现有：
`0` 参考(翻页不进队列) / `10` 第2档 / `20` 第3档 / `30` 第4档 / `40` 第6档 B1 /
`50` 第7档 B2 / `60` 解析预热。

拟增：

```kotlin
/** 面板在使用 ⇒ 读者此刻要它。池内最高，但仍让位翻页/栅格（号>0）。 */
const val PRIO_FONT_DEMAND = 5
/** 无人等 ⇒ 第 6.5 档：低于本章（40）/±1 章，高于其他章（50）。 */
const val PRIO_FONT_SCAN = 45
```

- `PRIO_FONT_DEMAND = 5` 落在 `PRIO_FLIP=0` 与 `PRIO_PAGE_NEXT=10` 之间：
  **池内最高，但不抢翻页**——`notifyFlip()`（`BookDocumentController.kt:1851`，
  `cancelLowerThan(PRIO_FLIP)`）仍能一刀砍它。这是对的：读者翻页 > 看面板。
- `PRIO_FONT_SCAN = 45` 即你定的「低于本章/±1 章，高于其他章」。
- 备选：面板需求也可放 `PRIO_PAGE_NEXT=10`（"读者下一步要用"档），但它会被
  `cancelForRaster` 一并砍；`5` 语义更干净。

### 3.2 机制：同键重提 = 提 / 降档（**无需新 API**）

`TaskScheduler.submit()`（`TaskScheduler.kt:114-140`）现有语义正好够用：

```kotlin
queue.removeAll { it.key == stamped.key && it.seq < mySeq }          // 旧的排队孪生踢掉
if ((runningSeq[stamped.key] ?: -1L) < mySeq) running[key]?.cancel()  // 旧的运行孪生就地取消
// 新任务按新 priority 入队（seq 决定谁赢）
```

⇒ **同一个 key `fontscan`，换 priority 重提，就是提档**；面板关闭=`cancelKey("fontscan")`。
不需要给调度器加「改优先级」新 API，也**不需要在视图层做闸门**——视图只说"面板开了/关了"。

### 3.3 必须**可续跑**（被抢占不丢成果）

`notifyFlip()` = `cancelLowerThan(0)`：砍掉池内**一切**后台；
`onForegroundRaster()`（`BookDocumentController.kt:1878`）= `cancelForRaster(0)`：
除 `pg:` 的 ±1 预排外全砍（`TaskScheduler.kt:199`）。

⇒ 扫描体必须**逐族落成果**：每完成一族就提交进指纹表 / DB；被抢占后重提**跳过已完成族**。
否则读一页书就被砍一次，永远跑不完。

现状 `NameTableChineseNames.chineseNames()`（`NameTableChineseNames.kt:30-32`）是
**全扫完才 publish**（`cache ?: scanAll().also { cache = it }`）——**这一点必须改为逐族增量发布**。

同一处机制同时服务两个目的：**抗抢占续跑** + **面板实时长出列表**。

### 3.4 触发矩阵

| 场景 | 触发 | key / 档 | 语义 |
| --- | --- | --- | --- |
| **面板打开** | 面板可见（Compose 可见性） | `fontscan` / **5** | 提档池顶，立即实扫；逐族增量刷新列表 |
| **面板关闭** | 面板不可见 | `fontscan` / **45**（同键重提＝降档） | 交出池顶；续跑不丢成果 |
| **启动一次性检测** | app 启动（只一次） | `fontscan` / **45** | 只比族名指纹（廉价）；变才全量增量扫 |
| **字体导入** | 本地 / Wi-Fi | 不进队列 | 立即刷新（用户直接动作） |
| **开书** | — | **无任何字体任务** | 这就是修 A |

## 4. 开书路径的两处修复

### 4.1 开书不再启动扫描

- 桌面：`ReaderView.kt:253-256` 的 `LaunchedEffect(book) { syncPanelFonts() }` **移除**；
- 平板：`ReaderActivity.kt:238-243`（`openBookEngine` 内的 F4c `syncSystemFaces`）**移除**，
  `loadPanelFonts`（`:496-501`，面板打开时重枚举）**保留**——它正是"面板需求模式"。

两者改为 ① app 启动检测 ② 面板可见性 驱动（§3.4）。面板读 DB；库冷时**不是占位**，是实时态（§2.4）。

### 4.2 引擎：判空提前到副作用之前

`BookDocumentController.kt:2982` `prepareRelayout` 现状——**先砍在途锚页，才发现是空章**：

```kotlin
// 现状（HEAD 66c6e90）
suspend fun prepareRelayout(chapter: Int, anchorChar: Int): ReflowResult? {
    clearFlipDir("param-change")
    preemptForNavigation()      // ← 砍在途后台
    layoutEpoch++               // ← 废在途锚页
    val myEpoch = layoutEpoch
    activeChapter = chapter     // ← 改成 0
    voidPreflight()             // ← 作废在途预排
    val unit = unitAt(chapter) ?: return null
    bindChapterFor(unit)
    val markup = unit.markup ?: return null   // ← 才在这里发现无 markup
    ...
```

拟改（**幂等早退**，返回 null 的路径不变，只是不再对空章产生副作用）：

```kotlin
// 拟改
suspend fun prepareRelayout(chapter: Int, anchorChar: Int): ReflowResult? {
    clearFlipDir("param-change")
    val unit = unitAt(chapter) ?: return null
    val markup = unit.markup ?: return null   // 无 markup：无事可做，副作用全免
    preemptForNavigation()                    // ↓ 以下顺序保持原样
    layoutEpoch++
    val myEpoch = layoutEpoch
    activeChapter = chapter
    voidPreflight()
    bindChapterFor(unit)
    ...
```

`prepareRelayoutLight`（`BookDocumentController.kt:2922`）同理——现为
`clearFlipDir → unitAt → bindChapterFor(unit) → markup 判空 → activeChapter = chapter`；
把 `bindChapterFor` 移到 `markup` 判空之后即可（`activeChapter = chapter` 已在判空后，无副作用暴露）。
`clearFlipDir` 本身只清方向记录（`BookDocumentController.kt:299`，无排版副作用），可保留在前面。

依据：`线程调度原则.md` §4「派发守卫——就地判据」。`unitAt` 只是
`chapters.getOrNull(index)`（`BookDocumentController.kt:3898`），前置无代价。

### 4.3（待拍板）闸门是否覆盖前台重排

`openAnchorGate` 目前只压 `requestWholeBookRelayout` / `dispatchB1`。
是否让它在开书落位在途时也把 `prepareRelayout*` 变成记账——涉及第 1 档内部仲裁语义，
**建议本方案先只做 4.2**（消除副作用），4.3 单列，不夹带，避免动到总则第 1 条。

## 8. 风险与待拍板

1. **抢占饥饿**：档 5 仍会被 `notifyFlip` / `cancelForRaster` 砍（号>0）。靠"逐族可续跑"化解；
   需定**成果提交点**（每族一次 DB 写 vs 攒批）。
2. **指纹假阴性**：同族名换文件（改 `name` 表但族名不变）检测不到。接受，或 P2 加文件 mtime 加固。
3. **首次冷库 + 立刻开面板**：可能与锚页落位（数百 ms）短暂争锁——重演 1.2 的迷你版。
   缓解：常态库热 ⇒ 不扫；4.3 若拍板"锚页优先"可彻底消。
4. **档位号 5 / 45 非十位**：`TaskScheduler` 注释称档号"留间隔（10/20/30/…）"，
   40→50 之间无空隙，故用 45 与 5；不建议整体重编号（动面大）。
5. **4.3 是否要做**：属第 1 档内部仲裁，建议单列，不夹带。
6. **首启库冷**：全新安装第一次打开面板前系统字体区为空——依赖 §2.4 实时态兜底；
   是否额外在首启调度一次预扫，待定。
