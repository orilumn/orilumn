> **判定标准**（用户裁定，2026-10-17）：引擎必须支持 HTML/CSS 的浏览器语义，

> [`文本标注与修订方案.md`](文本标注与修订方案.md)）。

>   把它算进去等于动全量基线，不值当；行内元素自带不同 `line-height` 比例的情形也按「继承比例」
>   建模（常见书写）。**表格格内**的行内大字号走同一个断行出口，一并生效。

#### E10–E12（第六刀，2026-10-18 实现）

> 这三条原先都在 C 表（「计算值在、绘制不消费」）。浏览器里它们的共同点是**只影响落墨、
> 不影响分行与分页** —— 这条性质决定了刀法：一律算成**随载体下发的绘制数据**，
> 绝不在排版几何上动手。

| # | 欠账（修前） | 浏览器语义 |
|---|---|---|
| **E10** | `ComputedStyle.visibilityHidden` 算得出来，但没有任何绘制方读它 ⇒ 书里写「隐藏」的段落照常显示 | `visibility: hidden` 的元素与其子树**不落墨但照占位**（与 `display: none` 的区别就在此）；后代可用 `visibility: visible` **单独翻回显示** |
| **E11** | `ComputedStyle.overflow` 算得出来，但没有裁剪路径 | `overflow != visible` 的盒把后代内容裁到自己的 **padding box**；链上**逐级求交**（祖先都裁） |
| **E12** | `ComputedStyle.positionRelative` 算得出来，但没有下游 | `position: relative` 相对**原位置**偏移（`top/right/bottom/left`），**不改排版**（占位与兄弟位置不动） |

**修法（已实现）**

- **E10**：新增按叶收集的**隐藏区间**（`VisibilityRuns.kt`，与行内盒 / 装饰收集同一套遍历骨架，
  隐藏状态沿祖先链继承、逐元素可覆写）；随 `DrawLine` 下发到落墨侧，绘制时跳过这些字符区间。
  行内盒**不删 run、只跳过绘制** ⇒ 横向推进量与显示时逐值相同（占位不变）。
- **E11**：新增单源 `OverflowClip.kt`（`ClipRect` + `paddingBox` / `inheritedClip` / `contentClipOf`
  / `clipMapOf` / `applyInheritedClips`）。重路径在**流完之后**算（盒上下沿由流决定，流前算即错位）；
  轻 / 临时路径的窗口盒是**窗口局部坐标**，由同源的窗口聚合表给出（不能读正典叶盒的裁剪字段，
  坐标系不符）。裁剪区**随载体带给渲染层**（文本行、盒底色/边框、插图、表格格内容与边框），
  落墨侧用**画布裁剪**施加 —— 不做矩形求交，是因为求交会切掉圆角、阴影与背景平铺原点。
- **E12**：新增单源 `RelativeOffset.kt`。偏移按**元素链**累积（匿名文本叶的样式是容器的副本，
  按盒累加会重复计一次），写进盒的绘制字段；消费点平移落墨几何并**同时平移页带**
  （等价「先偏移再裁」）。裁剪区随盒平移 ⇒ 必须先算偏移再算裁剪。

**验证**：`VisibilityHiddenTest`（10 例 × 双断行变体，含真栅格化与隐藏 `<li>` 不画 bullet）、
`OverflowClipTest`（8 例 × 双变体，含真栅格化「裁剪区外的墨被画布裁掉」与**重轻两路同几何**）、
`RelativeOffsetTest`（7 例 × 双变体，含「流几何逐值不变」与反空跑），外加
`TableCellLinesTest` 的格行裁剪 / 偏移 / 隐藏区间透传、`./gradlew jvmTest` 全量、
`:app:testDebugUnitTest`、`:app:assembleDebug`、真书离屏 `P5cOffscreenCorpusTest` 全绿。
**每一层都做过变异验证**（还原裁剪计算 / 逐行裁剪 / 轻路径裁剪源 / 偏移计算 / 盒平移 ⇒
对应用例当场变红）。

**近似与残留（记在案，别再当新发现）**

- **（E11 残留）** 表格 `td` **自身**的 `overflow` 不参与裁剪（格内容裁剪只取行叶的祖先链）；
  独图提升成 `<p>` 语境时没有盒，它自身的 `overflow` 不入表。
- **（E10 近似）** `visibility: collapse` 按 `hidden` 处理（本引擎没有表格行/列的折叠语义）。

  的**脱离流**布局、以及**层叠顺序 / `z-index`** 都不在本刀（绘制顺序仍是文档序）。
- **（E12 口径）** 表格 `tr` 自身声明相对定位时，格内容按行叶的累积偏移平移，
  与裁剪区的口径可能差这一层（`tr` 在本引擎里没有盒）。

## 4. 实现设计（第一刀：行内盒装饰）

> 动工前定稿的设计。目标：行内（非替换）元素的 `background-color` / `padding` / `border`
> 按浏览器语义绘制。

### 4.1 浏览器语义（只认这些）

以行内元素为单位，**逐行生成一个「行内盒片段」**：

| 项 | 语义 | 影响排版？ |
|---|---|---|
| **内容区** | 高度 = 该元素**自身字体**的 em 盒（`ascent + descent`），**不是行高** | 否 |
| **纵向 `padding`/`border`** | 向外扩张，**不撑高行框**（与邻行重叠——浏览器如此） | 否 |
| **横向 `padding`/`border`** | 加宽该行内盒，**后续文字右移**（参与断行宽度） | **是** |
| **背景** | 铺满 **border-box**（默认 `background-clip: border-box`），含 padding 与 border 区 | 否 |
| **四边边框** | `border-top/bottom` 在**每个片段**上；`border-left` 只在**首片段**、`border-right` 只在**末片段**（`box-decoration-break: slice` 默认） | 纵向否 / 横向是 |

### 4.2 动工前的现状缺口（侦察结论；**已被第一刀 1a/1b 修掉，留作史料**）

- **样式值已就绪**：`ComputedStyle` 上 `backgroundColorHex`、`padding: Edges`、`border: Edges`、
  `borderColors`/`borderStyles` 都已算（`ComputedStyle.kt:228-243`），行内元素也一样算。
- **缺「行内盒」这个对象**：`isInline`/`InlineBox` 全仓零命中；背景属主只从**叶向上找祖先**
  （`BoxChapterLayouter.kt:499-510`），行内后代永不被认领 ⇒ `<mark>` 有 UA 规则但画不出来
  （`ua.css:63-64` 自注「行内背景绘制属缺口，先落规则占位」）。
- **缺绘制路径**：`LineWindowDrawer` 里没有任何行内背景/边框绘制；`DrawLine` 也没有对应字段。
- **横向边距未进 measure**：`innerBreakWidth`（`NormalFlowLayout.kt:1466`）只减**块盒**

### 4.3 数据模型（渲染层）

新增与 `UnderlineRun` 同构、挂在 `DrawLine` 上的行内盒 run：

```kotlin
// engine-skia：随 DrawLine 下发的行内盒片段（叶文本坐标系，与 range / underlineRuns 同源）
data class InlineBoxRun(
    val start: Int, val endExclusive: Int,
    val bgArgb: Int?,                                  // 背景色（已解析；null = 无）
    val padTop: Float, val padRight: Float, val padBottom: Float, val padLeft: Float,
    val borderTop: Float, val borderRight: Float, val borderBottom: Float, val borderLeft: Float,
    val borderArgb: Int,                               // currentColor 已在收集时解析
    // 该片段的字体（决定 em 盒高度）；z 序按区间先后
    val fontSizePx: Float, val families: List<String>, val weight: Int,

```

- **只对有可见物的元素发 run**（`backgroundColorHex != null || hasBorderEdges()`）
  ⇒ `<em>` / `<a>` 这类无装饰的行内元素**零开销**。
- 「首 / 末片段」**不预存**：绘制时用该行裁剪区间与 `start`/`endExclusive` 比对即得。
- 边框样式 **v1 只认 `SOLID`**（与其他样式的差距另记，不装看不见）。

| 步 | 内容 | 排版影响 | 状态 |
|---|---|---|---|
| **1a** | 行内背景 + 四边边框 + padding 的**绘制**（跨行按 `slice` 拆片段） | **无** | 已实现 |
| **1b** | 横向 `padding`/`border` 参与**横向排版**（断行 / 推进） | **有** | 已实现 |

#### 1b 的机制（唯一口径，别改散）

- **推进量载体**：把叶文本坐标系的盒折算成**稀疏边缘表**（逐字位增量），而不是传「盒」本身。
  盒的**左边**推进量记在 `start − 1`、**右边**记在 `endExclusive − 1`（与混排字距同一施加规则：
  `x_i = x_0 + Σ_{j<i} adv[j]`，记在边界左侧那个字位才推得动后续文字）。
- **切片即 `slice` 语义**：推进量**按叶坐标算一次**、落墨与断行时按行裁。盒从上一行延续过来时，
  它的左边推进量落在切片之外 ⇒ **续片段天然没有左边框/内边距**；右边同理只在末片段生效。
  若改成传「盒」、再在行内判断「是否真起点」，续片段会被误判为起点而多画一条左边框 ⇒ 一律切表。
- **起始于叶首字符的左边内边距**（盒从叶首字符起）无处可记（advance 数组表达不了「首行之前」），
  折入**首行缩进**通道：语义上正是「首行起始位移 + 首行减宽」，与 `text-indent` 同一件事。
  **断行侧与落墨侧各折一处、共用同一函数**（量画同源）。嵌套盒自然按外 + 内求和叠出层级。
- **三路同源**：断行器（为推进量预留版心）、落墨落位（算每字 x）、簇位轨（kerning 轨迹）三条路
  都走**同一个取宽出口**，推进量**只在该出口施加一次**（施加在混排字距之后，避免被「吃掉分隔空格」
  的置零抹掉）。簇位轨必须同步补推进量，否则它会把注入量当成字体收紧量吃掉。
- **回退纪律（重要）**：既有的「退回旧断行方式」开关关掉时，两侧必须**一致地不参与** ——
  推进量在**推导处**（而非各处调用点）统一判空。理由与混排字距相同：旧断行方式拿 `SkParagraph`
  自量版心，本仓无法让它为注入的推进量预留宽度；只关断行侧而落墨侧照旧施加，就是
  **画比量宽 ⇒ 右溢被裁**（分页阅读器无横向滚动条，溢出即丢字）。关闸时行内盒**只画不推**
  （即 1a 行为），字不会丢。
- **零回归**：横向边距为 0 的盒（`<mark>` 只有底色、`border-bottom` 只有下边框）产出**空表**
  ⇒ 像素与 1a 逐值相同（1a 那一步「横向边距为 0 ⇒ 零推进」是这一刀零回归的关键前提）。
  本机制只对显式设了行内横向 `padding`/`border` 的书生效。
- **shrink-to-fit 同步**：不换行内容的首选宽度（悬浮盒定宽、表格 auto 分列的 max-content）
  也把横向内边距/边框计入，否则盒按「没有内边距」定宽而落墨照样推开 ⇒ 内容溢出盒右缘。

#### 已知剩余缺口（记在案，别再当新发现）

- **（E15）表格 auto 分列的单元格 max/min-content** 未计入格内**行内盒**的横向内边距：该路径只有断行器
  与块表，拿不到「叶文本坐标系」的行内盒（匿名 run 的文本坐标与容器文本坐标存在偏移风险）。
  症状限于「表格里的行内盒可能窄一点」，方向不会反向到丢字（不换行溢出本就是浏览器行为）。
- **（E16）行内盒的虚线/点线边框**暂按实线画（只把 `border-style: none/hidden` 判为不画）：块盒的
  `BoxDrawer` 已能画 `dashed`，行内盒这一步没做。低频，随后续小刀补齐（已进 §2.1 总账）。
- **（E17）行内盒暂无 `border-radius`**（画方角）：块盒有圆角绘制，行内盒的片段圆角未做。
- 纵向 `padding`/`border` 按浏览器语义**不撑高行框**（与相邻行重叠），本轮照此实现，不是缺口。
