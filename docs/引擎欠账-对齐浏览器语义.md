# 引擎欠账：对齐浏览器语义（0.4.6 交付）

> **判定标准**（用户裁定，2026-10-17）：引擎必须支持 HTML/CSS 的浏览器语义，
> **EPUB2/3 范围内的渲染功能都要实现**；文本背景也是 HTML/CSS 规范的一部分。
> 据此，凡「书里写了、浏览器会画、我们画不出或画错」的，都是欠账。
>
> 计划版本：**0.4.7**（实际随 **0.4.6** 交付）。记录日期：2026-10-17；现状 `orilumn.versionName = 0.4.6`。
>

> [`文本标注与修订方案.md`](文本标注与修订方案.md)）。

#### E10–E12（第六刀，2026-10-18 实现）

> 这三条原先都在 C 表（「计算值在、绘制不消费」）。浏览器里它们的共同点是**只影响落墨、
> 不影响分行与分页** —— 这条性质决定了刀法：一律算成**随载体下发的绘制数据**，
> 绝不在排版几何上动手。

| # | 欠账（修前） | 浏览器语义 |
|---|---|---|
| **E10** | `ComputedStyle.visibilityHidden` 算得出来，但没有任何绘制方读它 ⇒ 书里写「隐藏」的段落照常显示 | `visibility: hidden` 的元素与其子树**不落墨但照占位**（与 `display: none` 的区别就在此）；后代可用 `visibility: visible` **单独翻回显示** |
| **E11** | `ComputedStyle.overflow` 算得出来，但没有裁剪路径 | `overflow != visible` 的盒把后代内容裁到自己的 **padding box**；链上**逐级求交**（祖先都裁） |
| **E12** | `ComputedStyle.positionRelative` 算得出来，但没有下游 | `position: relative` 相对**原位置**偏移（`top/right/bottom/left`），**不改排版**（占位与兄弟位置不动） |

**修法（已实现）**

- **E10**：新增按叶收集的**隐藏区间**（`VisibilityRuns.kt`，与行内盒 / 装饰收集同一套遍历骨架，
  隐藏状态沿祖先链继承、逐元素可覆写）；随 `DrawLine` 下发到落墨侧，绘制时跳过这些字符区间。
  行内盒**不删 run、只跳过绘制** ⇒ 横向推进量与显示时逐值相同（占位不变）。
- **E11**：新增单源 `OverflowClip.kt`（`ClipRect` + `paddingBox` / `inheritedClip` / `contentClipOf`
  / `clipMapOf` / `applyInheritedClips`）。重路径在**流完之后**算（盒上下沿由流决定，流前算即错位）；
  轻 / 临时路径的窗口盒是**窗口局部坐标**，由同源的窗口聚合表给出（不能读正典叶盒的裁剪字段，
  坐标系不符）。裁剪区**随载体带给渲染层**（文本行、盒底色/边框、插图、表格格内容与边框），
  落墨侧用**画布裁剪**施加 —— 不做矩形求交，是因为求交会切掉圆角、阴影与背景平铺原点。
- **E12**：新增单源 `RelativeOffset.kt`。偏移按**元素链**累积（匿名文本叶的样式是容器的副本，
  按盒累加会重复计一次），写进盒的绘制字段；消费点平移落墨几何并**同时平移页带**
  （等价「先偏移再裁」）。裁剪区随盒平移 ⇒ 必须先算偏移再算裁剪。

**验证**：`VisibilityHiddenTest`（10 例 × 双断行变体，含真栅格化与隐藏 `<li>` 不画 bullet）、
`OverflowClipTest`（8 例 × 双变体，含真栅格化「裁剪区外的墨被画布裁掉」与**重轻两路同几何**）、
`RelativeOffsetTest`（7 例 × 双变体，含「流几何逐值不变」与反空跑），外加
`TableCellLinesTest` 的格行裁剪 / 偏移 / 隐藏区间透传、`./gradlew jvmTest` 全量、
`:app:testDebugUnitTest`、`:app:assembleDebug`、真书离屏 `P5cOffscreenCorpusTest` 全绿。
**每一层都做过变异验证**（还原裁剪计算 / 逐行裁剪 / 轻路径裁剪源 / 偏移计算 / 盒平移 ⇒
对应用例当场变红）。

**近似与残留（记在案，别再当新发现）**

- **（E11 残留）** 表格 `td` **自身**的 `overflow` 不参与裁剪（格内容裁剪只取行叶的祖先链）；
  独图提升成 `<p>` 语境时没有盒，它自身的 `overflow` 不入表。
- **（E10 近似）** `visibility: collapse` 按 `hidden` 处理（本引擎没有表格行/列的折叠语义）。
- **（E12 残留）** 只做 `position: relative`：`%` 偏移（需按包含块尺寸解算）与 `absolute` / `fixed`
  的**脱离流**布局、以及**层叠顺序 / `z-index`** 都不在本刀（绘制顺序仍是文档序）。
- **（E12 口径）** 表格 `tr` 自身声明相对定位时，格内容按行叶的累积偏移平移，

#### E21（`::first-letter` 真正支持，2026-10-19）

> 第二刀（E6）把伪元素收紧成「整条不匹配」，治住了「首字规则套整段」的画错，
> 但浏览器会画的效果我们仍然不画 —— 验收样书 V2 节的首字下沉示例因此落空。

- **语义口径**：`::first-letter` 命中「首个真实文字段的首个字素簇」（前导引号等标点一并算入，
  与 CSS 原生口径一致），命中段以**带样式的字符段**进入既有收集/绘制管线（与链接、装饰同骨架），
  `br`/`img` 等标记段跳过；**段落其余文字与整段版面照旧**（首字放大时只有首行行框按 §10.8 撑高）。
- **闸门**：级联出口「本章有无 `::first-letter` 规则」按章缓存 —— 没有这类规则时整条链路
  不建不查，**零开销**；有规则但未命中时不拆段（单段原样）。
- **`float:left` 首字下沉（2026-10-20 实现）**：首字**浮出成独立浮动盒**，与浏览器同构 ——
  ①首字仍是叶文本第 0 位（首行里占的就是自己的推进量，浏览器算出的下沉盒宽也正是这个推进量，
  故首行既不收窄也不偏移）；②自第 1 行起，收窄并右移一个下沉盒宽的**后续行数** =
  `ceil(下沉盒高 / 正文字行高) - 1`（18px/1.5、首字 2em ⇒ 压住 2 行）；③首字出流，
  **不撑首行行框、不抬首行基线**，自己按「盒顶 = 首行行框顶、盒内按半行距居中」的基线落墨
  （Chromium 实测：首字基线比正文低 14 CSS px，同式）。
  重/轻两路同一份推算（盒流与塑形侧各算一次同源值，落在盒/塑形结果上），绘制只读不推。
- **验证**：`SelectorSemanticsTest`（路由与段落本体反例）、`FirstLetterSegmentsTest`（拆段全文一致 /
  标记段跳过 / 级联命中与未命中 / 叶行高）、`FirstLetterEndToEndTest`（整段字号不变、首字单 run、

  首字高 27px、正文约 14px（恰好 2 倍；字体与浏览器不同，绝对值不逐像素对齐）。

#### 真书命中复核（2026-10-18，第六刀复查）

> 目的：确认这三条补的是**真问题**而不是自嗨。做法：把 `books/` 语料逐本解包按声明扫 CSS，
> 再用**离屏全管线像素 A/B**（同一构建、同一台机器，只开关 E11 的裁剪计算与 E12 的偏移计算）对照。

- **`overflow`**：语料 11 本里**活的非 `visible` 声明只有一处** —— `internallinks.epub` 的

#### E20（第六刀复查真书命中时实测发现，2026-10-18，已修一半）

> 这条**不是** E11 的实现 bug，而是 E11 让一条**老缺口**从「画错」升级成「丢内容」：
> 引擎的流**有意**不做 BFC 包拢（浮动逃逸容器），于是裁剪盒按 padding box 硬裁会把浮动齐根切掉。

| # | 欠账（修前） | 浏览器语义 |
|---|---|---|
| **E20** | 盒的自动高度**只计在流内容**，浮动后代不参与 ⇒ 裁剪盒的 padding box 底部可能高于浮动 ⇒ E11 的裁剪**把浮动整块切掉**（文字块、图片、列表项都会中招）。引擎自己的注释早已写明「包住只在 BFC/clearfix，本引擎无此概念」 | CSS 2.1 §10.6.7：`overflow != visible` 的块建立 BFC，自动高度**包住浮动后代**（`overflow: visible` 的块按 §10.6.3 不包，浮动照旧溢出容器） |

**为什么必须修**：真书里的 **clearfix** 写法就是「裁剪容器里全是 `float` 子块」，此时在流高约等于 0
⇒ 裁剪下沿 ≈ 0 ⇒ **整块内容消失**。实测：图片浮动高 120 被裁到 61（重路径）、53（**显示用的轻路径**）；
只浮动列表项时第三项被切。用户裁定的优先级里「丢字级 > 一切画错级」，故本轮当场修掉。

**修法（已实现）**

- **重路径**：`NormalFlowLayout` 在流完之后补一趟 `containFloatsInClippers` —— 对每个
  `overflow != visible` 的盒，把**内容盒底**抬到「最深浮动后代 border-box 底」，再加回自身下边距
  （裁剪区取 padding box，少算边框会把浮动最下几像素切掉，实测差 2px）。
- **轻路径**：窗口画盒聚合按「叶 → 行区间」推位置，而**替换型浮动叶（图）在行流里只有零高行**
  ⇒ 聚合不到它。`extentOf` 对这类叶按替换高还原真实下沿（文本浮动叶的行本来就是真的，无需还原）。
- 盒高既管**绘制**（底色 / 边框 / 裁剪区）也管**流**（父容器高度、后随内容、分页）——
  浏览器就是一份高度；2026-10-20 前只改绘制，容器下沿因此比浏览器高出几像素；
  重轻两路裁剪同高（新锁逐值断言）；**BFC 根同时把盒内浮动关在盒内**（收窄/回填只作用于盒内，
  进入时存外层跨度、收尾还原），否则后随段落会被盒内的浮动拉回跨度顶、压在容器里。

**残留（记在案，别再当新发现）**

- **（E20 残留 a）非裁剪容器仍不包浮动**：重路径按 §10.6.3（正确）；但**轻路径**的背景带对
  任何 `overflow` 值都把浮动算进聚合 ⇒ 「有底色/边框的 `overflow: visible` 容器 + 浮动」两路分叉
  （实测：`div` 背景重路径 y ∈ [19,66]，轻路径 [19,215]）。改这条会动到既有语料的底色范围，
  单独一刀再动。
- **（E20 残留 b）同侧浮动兄弟的纵向堆叠与自身顶边距次序两路不同**：重路径**先堆叠再加边距**，
  轻路径**先加边距再取较大** ⇒ 带纵边距的浮动兄弟位置分叉（实测列表项：重路径 27 / 74 / 121，
  轻路径 27 / 55 / 83）。同样是既有分歧，与 E20 的修法无关。
- **（E20 残留 c）真正的 BFC 还有别的分支**：不与子盒折叠外边距、`clear` 的生效范围、
  `float` 后代**自身**的 `overflow` 裁剪，都不在本刀。
- **（E20 残留 d）`position: absolute` 后代不该被祖先 `overflow` 裁**（CSS 2.1 §11.1.1：
  绝对定位后代不被「它与包含块之间」的祖先裁剪）—— 本引擎没有 `absolute` 布局，记着即可。
- **（E20 残留 e）`float` 作用在行内元素**（真书的下沉首字与行号）：「计算成 `display: block`」
  这一条是否已成立**尚未核**，需单独侦察（真书命中见上）。

  重/轻盒宽会分叉（`P6aFloatTest` 当场变红），故新增 `lightSpecifiedWidth` 与重路径逐条对齐。

**③ E12 备注（行内相对定位，第六刀遗漏的一半）**

第六刀的偏移只沿 **`LayoutBox`**（块级盒）累积；而 `<span class="rel">` 是**行内盒**，
叶块（`p`）的祖先链里没有它 ⇒ **行内元素的 `top/left` 整条不生效**（验收样书 V6 的 `.rel` 不动）。
补法：行内盒 run 新增 `relDx/relDy`（取「本元素 + 其**行内**祖先到叶块为止」的累积，
块级祖先那部分已在 `LayoutBox.relOffset*` 里平移整行，不重复计），落墨侧三处一起用 ——
行内盒底色/边框、逐字 `dx/dy`（按字符区间求和，嵌套自然叠加）、批处理的 y 变化自动断批。
**实测**：`.rel` 盒从 `x[65,144] y[419,447]` 平移到 `x[77,156] y[425,453]` = **+12/+6**，
盒外文字仍在原基线（流几何零变化）。

**绘制层级（2026-10-20 补）**：相对定位盒按 CSS 2.1 附录 E **第 8 步**画，即在流内容（第 7 步）
**之后** —— 盒的底色/边框盖住与它重叠的在流文字（CSS Position 3 §2.2：`z-index: auto` 的相对/
绝对定位盒「painted as if it generated a new stacking context」）。引擎原先与其它行内盒一起垫在
文字下，重叠处被后文压住（Calibre / Chromium 都压在上面）。现把**有位移**的已定位 run 拆第二趟：
`盒 → 自己的字`，在流那趟跳过这些区间（连同其装饰线，避免叠深）。第二趟必须排在**整块**在流
内容之后（页面级两趟，不是逐行两趟）—— 盒下移会压到**下一行**，逐行画时下一行的字会把盒盖回去。判据用 run 的累积 `relDx/relDy`
（零位移的已定位盒画哪层都看不出差别，不为它多开一趟）。同段两趟绘制时塑形槽位按段落起点偏移
索引（`graftKerningOnto` 的 `off/count`）。锁：`InlineBoxPaintTest.已定位行内盒压在在流文字之上、
自己的字压在盒上`（变异：强制单趟 ⇒ 变红）。

**行内偏移的残留**：①**装饰线 / 着重号 / 注音**仍按原位置画（它们各自有独立的落墨路径，
不走逐字位移表）；②**命中测试**按原字位判定，偏移过的字上点按会落到邻近字位。

**④ E22-b 零行盒**

`.cf`（clearfix）与空浮动方块都是**不产行、但有 border-box** 的盒；页带越界判定原先只看行区间相交
（`lastLineExclusive <= pageStartLine` 对零行盒恒真）⇒ 它们**永远被判为不在本页**，整块不落墨。
改为零行盒按端点 `k` 归属（`k ∈ (pageStart, pageEnd]`，交界归前一页）。修后无头像素里
`.cf` 与四个浮动方块重新出现。

**⑤ E23 叶 / 浮动盒指定高**

`height` 原先只在**行**上被消费：叶与浮动盒的底边跟着内容走，`.fl{height:30px}` 的方块塌成
两条边框。口径与容器同一条「只多不少」——内容盒高 = max(在流内容高, `height`)，内容更高照排不裁；
跨度（浮动占位）与画盒同吃这一份。无头像素（验收样书 V6）：四个方块 30/40 + 2px 边框与 Chromium
同值（`.fl` 边框环 30 高、`.fli` 40 高）。

**⑥ E23-c 同侧浮动行装箱**

并排不是「补个行装箱」就完，本轮探到三条前提并**一并做掉**：

1. **空浮动盒先要真的当浮动盒**：`<div class="fl">` 无文本无图时过不了重路径 `emit` 的浮动闸门
   （原判据 `replaceableHeight > 0 || ranges.isNotEmpty()`）⇒ 被当**普通块顺排**（推进流游标），
   这就是「四个方块纵向叠」的直接原因。闸门放宽到「空盒 + 指定高 > 0」，重/轻两路同判据；
   空浮动盒**不再发行**（重路径新加守门、轻路径本来为 0），与普通无行盒一样走端点记账。
2. **`FloatPending` 由单列升级为行装箱**（CSS 2.1 §9.5.1）：同侧同行放得下 ⇒ 本行 x 累加、同顶、
   行高取 max，**第二块起不再加自身顶边距**；放不下或被文本越过（本行已被文本吃掉）⇒ 另起一行，
   新行顶 = 当前文本游标（旧「旧余量 + 新高」口径原样保留，只多不少仍朝安全方向）。
   记账一律按**外边盒**宽（左右外边距参与排位，容量 = 含边距的包含块内容宽）。
3. **轻路径浮动画盒宽度**：原先 `buildBackgroundDrawBoxes` 的盒宽走 `ownerBackgroundBox` →
   `descendContentWidth`，而浮动不消费指定宽 ⇒ 轻路径浮动底盒是**满宽**（重路径 30px）。
   本轮让 `ownerBackgroundBox` 也走 eager 表给的悬浮自身宽与落点（磁盘表页看不出，临时/增量页
   原先会画成整行色带）。轻路径 eager 表新增 `floatXOffs`/`floatNewRows` 两张表，与重路径
   `buildBoxTree` 的 `register` 单源同值。

无头像素（验收样书 V6，视口 760×1000）：四个方块回到**同一行**，`.cf` 底色带 h=**54**
（Chromium 同级 54）。间距 = 每盒「border-box + 左右外边距」（E24 起 border-box 含自身横边，
方块的边框环并集 68×32 / 88×42 已与 Chromium 逐值相同，见 ⑨）。

**⑦ E23-b 容器指定高**

`height` 原先只在**叶/浮动盒**上消费（A 表 E23），**容器**（非叶，如 `.ovh{height:40px}`）的底边仍
跟着内容走 ⇒ 内容只有一行 27px 时盒子只有 35px 高（Chromium 50px）。容器分支整体照搬叶的口径即可
（内容盒高 = max(在流内容高, `height`)，游标只下不上 ⇒ 行位单调、分页容量仍由行位给出）。

真正的难点在**轻路径**：它的行流是局部位移累加（`consecutiveLeafAdvance` 只认边距与边），
「容器内容有多高」没有现成值 —— 这正是当初记为残留的原因。做法是把重心从「算内容高」挪到
**「记边界差额」**：建一张按**块下标**记的前缀表 `containerHeightLead[b]` = 进入块 b 之前闭合的
所有容器差额之和，三处消费（行流推进、`blockBoundaryGap`/`interiorGapAbove`、画盒带）。

- 差额 = `height − 内容高`（仅当内容更矮）；内容高按行流同一套算术累计：首子链下沉 + 首叶 top 边
  + Σ(叶内容盒高 + 叶下边 + 块间 advance + 后叶 top 边)。
- **内层先算**（叶区间短的先）：内层盒子本来就是外层的内容，内层差额写进前缀表后，外层累计到
  那个边界时自然吃到它 ⇒ 嵌套容器一次前向扫描就对。
- **早退**：内容高累计一旦达到指定高就停（差额 0），所以开销以「填满指定高所需的那几叶」为界；
  内容更矮时本来就没几叶。常书连这一步都不做 —— `chapterHasBoxHeight` 门在
  「样式表有能出 px 的 `height` 声明 / inline style 提到 height」上，`img{height:100%}` 这类
  百分比写法被特意排除（`parseBoxSize` 给 `heightPx = null`）。
- 顺带修一处 §8.3.1 口径：父↔末子**底**折叠要求父 `height:auto`，指定高与底边同权**断链**
  （重路径 `lastChildBottomMargin`、轻路径 `consecutiveLeafAdvance` 两处同判据）。

无头像素（验收样书 V6）：`.ovh` 的 `#333` 边框环 `x[10,120] y[361,411]` = **110×50**，
与 Chromium `x[25,134] y[261,310]`（110×50）同值（修前 110×38）。

**⑧ E23-e 竖向下限（`min-height`）**

`min-height` 与 `height` 同属「竖向占位」，但两者的**底折叠口径不同**，先量后写（Chromium
`--headless=new`，2026-10-20，正文字号 16px/行高 20px，末子 `margin-bottom` 20/60/100 三档）：

| 写法（内容高 20） | 盒高 | 后随内容相对盒底 |
|---|---|---|
| `min-height:120` | **120** | **0**（末子下边距收进盒内，不外塌） |
| `min-height:30`（> 内容 20） | **30** | **0** |
| `min-height:10`（≤ 内容 20） | **20** | **20**（照常外塌） |
| `height:20` + `min-height:40` | **40** | 0（`min-height` 压过 `height`） |
| `height:20`（内容 40） | 20 | 0（定高与内容无关，恒断链） |
| 仅浮动子 + `min-height:80` | **80** | 0 |

⇒ 引擎口径：内容盒高 = max(在流内容高, max(`height`, `min-height`))；折叠判据**两档** ——
`height` 声明即断链，`min-height` 只在**下限 > 自然内容高**（真的撑高）时断链。仅浮动子时 floater
不进在流内容高，`min-height` 直接成为盒高（与 `height` 同式）。

落地：`specifiedVerticalFloor` 单源给出下限（两者皆无 ⇒ null，0 与 null 分开），
`specifiedContentHeight` = max(自然高, 下限) 供叶 / 浮动盒 / 容器三处共用；折叠结论一旦算出就
**带在盒上**（重路径 `LayoutBox.verticalFloorBound`，轻路径 `LightPrepare.floorBoundContainers`），
`lastChildBottomMargin` 与 `consecutiveLeafAdvance(floorBinds = …)` 读同一份结论 —— 轻路径的
`floorBoundContainers` 由差额表顺带填（`content < h` 即撑高），三处调用点（块间落差、行流推进、
差额累计）全部传入，避免重/轻分叉。总闸 `chapterHasBoxHeight` / `hasBoxHeightDeclaration` 认
`min-height`；顺手修掉该闸门把「非 `height` 属性的任意声明」当命中的旧笔误（否则常书恒真、白扫一遍）。

`max-height` 仍不做：浏览器是「裁切 + 溢出」，要连带决定内容被收掉后游标往哪走，与这里「只多不少」
不是一套机理（D 表，已裁定）。

**⑨ E24 浮动盒的内容盒宽**

Chromium 实测（`--headless=new`，760×1000，`.fl{width:30px;height:30px;border:1px;margin:2px}`）：
`width` 是**内容盒**宽 —— 底色 30px、边框**外画**、外框 **32px**；两个并排的边框环并集 **68×32**
（32 + 4 + 32），`.fli{width:40px;border:1px}` 同理 **88×42**。我方原先把 `width` 当 border-box
（外框 30px），于是每盒少自身横边 2px：并排间距少 2px、**浮动内容区小 2px**（浮动文本提前折行）。

落地：单源 `floatBorderBoxWidth(style, contentW)` 做「内容宽 → border-box」的反算，四处消费同一份 ——
① 重路径 `buildBoxTree` 的文本浮动与替换型浮动（盒宽 / 落点 / 外边盒记账）；
② 轻路径 `computeFloatLeads` 的同一对照表（宽 / 落点 / 行装箱容量）；
③ 画盒（`ownerBackgroundBox` → `floatBoxOf` 的宽与落点）；
④ 环绕前导（`floatLeadFor` / `FloatPending` 的窄宽按 border-box 收窄）。
断行宽仍由 `innerBreakWidth(style, borderBox)` 反算回内容宽（30px，不是 28px）——量画同源。

无头像素（验收样书 V6）：两个 `.fl` 边框环并集同一次构建的引擎 PNG 与 Chromium **逐值相同**
（68×32、88×42；改前 64×30 / 84×40），四个方块仍在同一行、`.cf` 底色带 h=54 不变。
新增 `FloatBorderBoxWidthTest` 五例（重/轻盒宽与落点、画盒宽、断行宽、环绕前导、章首页切片）。

**残留：无**（待补表已清零；`max-height` 与「文本浮动盒行发射口径」见 D 表）

## 4. 实现设计（第一刀：行内盒装饰）

> 动工前定稿的设计。目标：行内（非替换）元素的 `background-color` / `padding` / `border`
> 按浏览器语义绘制。

### 4.1 浏览器语义（只认这些）

以行内元素为单位，**逐行生成一个「行内盒片段」**：

| 项 | 语义 | 影响排版？ |
|---|---|---|
| **内容区** | 高度 = 该元素**自身字体**的 em 盒（`ascent + descent`），**不是行高** | 否 |
| **纵向 `padding`/`border`** | 向外扩张，**不撑高行框**（与邻行重叠——浏览器如此） | 否 |
| **横向 `padding`/`border`** | 加宽该行内盒，**后续文字右移**（参与断行宽度） | **是** |
| **背景** | 铺满 **border-box**（默认 `background-clip: border-box`），含 padding 与 border 区 | 否 |
| **四边边框** | `border-top/bottom` 在**每个片段**上；`border-left` 只在**首片段**、`border-right` 只在**末片段**（`box-decoration-break: slice` 默认） | 纵向否 / 横向是 |

### 4.2 动工前的现状缺口（侦察结论；**已被第一刀 1a/1b 修掉，留作史料**）

  `borderColors`/`borderStyles` 都已算（`ComputedStyle.kt:228-243`），行内元素也一样算。
- **缺「行内盒」这个对象**：`isInline`/`InlineBox` 全仓零命中；背景属主只从**叶向上找祖先**

```kotlin
    val padTop: Float, val padRight: Float, val padBottom: Float, val padLeft: Float,
    val borderTop: Float, val borderRight: Float, val borderBottom: Float, val borderLeft: Float,
    val borderArgb: Int,                               // currentColor 已在收集时解析
    // 该片段的字体（决定 em 盒高度）；z 序按区间先后
    val fontSizePx: Float, val families: List<String>, val weight: Int,
    val italic: Boolean, val monospace: Boolean,
)
```

- **只对有可见物的元素发 run**（`backgroundColorHex != null || hasBorderEdges()`）
  ⇒ `<em>` / `<a>` 这类无装饰的行内元素**零开销**。
- 「首 / 末片段」**不预存**：绘制时用该行裁剪区间与 `start`/`endExclusive` 比对即得。
- 边框样式 **v1 只认 `SOLID`**（与其他样式的差距另记，不装看不见）。

### 4.5 分两小步交付（均已实现）

| 步 | 内容 | 排版影响 | 状态 |
|---|---|---|---|
| **1a** | 行内背景 + 四边边框 + padding 的**绘制**（跨行按 `slice` 拆片段） | **无** | 已实现 |
| **1b** | 横向 `padding`/`border` 参与**横向排版**（断行 / 推进） | **有** | 已实现 |

#### 1b 的机制（唯一口径，别改散）

- **推进量载体**：把叶文本坐标系的盒折算成**稀疏边缘表**（逐字位增量），而不是传「盒」本身。
  盒的**左边**推进量记在 `start − 1`、**右边**记在 `endExclusive − 1`（与混排字距同一施加规则：
  `x_i = x_0 + Σ_{j<i} adv[j]`，记在边界左侧那个字位才推得动后续文字）。
- **切片即 `slice` 语义**：推进量**按叶坐标算一次**、落墨与断行时按行裁。盒从上一行延续过来时，
  它的左边推进量落在切片之外 ⇒ **续片段天然没有左边框/内边距**；右边同理只在末片段生效。
  若改成传「盒」、再在行内判断「是否真起点」，续片段会被误判为起点而多画一条左边框 ⇒ 一律切表。
- **起始于叶首字符的左边内边距**（盒从叶首字符起）无处可记（advance 数组表达不了「首行之前」），
  折入**首行缩进**通道：语义上正是「首行起始位移 + 首行减宽」，与 `text-indent` 同一件事。
  **断行侧与落墨侧各折一处、共用同一函数**（量画同源）。嵌套盒自然按外 + 内求和叠出层级。
- **三路同源**：断行器（为推进量预留版心）、落墨落位（算每字 x）、簇位轨（kerning 轨迹）三条路
  都走**同一个取宽出口**，推进量**只在该出口施加一次**（施加在混排字距之后，避免被「吃掉分隔空格」
  的置零抹掉）。簇位轨必须同步补推进量，否则它会把注入量当成字体收紧量吃掉。
- **回退纪律（重要）**：既有的「退回旧断行方式」开关关掉时，两侧必须**一致地不参与** ——
  推进量在**推导处**（而非各处调用点）统一判空。理由与混排字距相同：旧断行方式拿 `SkParagraph`
  自量版心，本仓无法让它为注入的推进量预留宽度；只关断行侧而落墨侧照旧施加，就是
  **画比量宽 ⇒ 右溢被裁**（分页阅读器无横向滚动条，溢出即丢字）。关闸时行内盒**只画不推**
  （即 1a 行为），字不会丢。
- **零回归**：横向边距为 0 的盒（`<mark>` 只有底色、`border-bottom` 只有下边框）产出**空表**
  ⇒ 像素与 1a 逐值相同（1a 那一步「横向边距为 0 ⇒ 零推进」是这一刀零回归的关键前提）。
  本机制只对显式设了行内横向 `padding`/`border` 的书生效。
- **shrink-to-fit 同步**：不换行内容的首选宽度（悬浮盒定宽、表格 auto 分列的 max-content）
  也把横向内边距/边框计入，否则盒按「没有内边距」定宽而落墨照样推开 ⇒ 内容溢出盒右缘。

#### 当时的剩余缺口（**三条均已于 2026-10-18 补齐**，见 A 表 E15–E17；下面留作史料）

- **（E15）表格 auto 分列的单元格 max/min-content** 未计入格内**行内盒**的横向内边距：该路径只有断行器
  与块表，拿不到「叶文本坐标系」的行内盒（匿名 run 的文本坐标与容器文本坐标存在偏移风险）。
  症状限于「表格里的行内盒可能窄一点」，方向不会反向到丢字（不换行溢出本就是浏览器行为）。
- **（E16）行内盒的虚线/点线边框**暂按实线画（只把 `border-style: none/hidden` 判为不画）：块盒的
  `BoxDrawer` 已能画 `dashed`，行内盒这一步没做。低频，随后续小刀补齐（已进 §2.1 总账）。
- **（E17）行内盒暂无 `border-radius`**（画方角）：块盒有圆角绘制，行内盒的片段圆角未做。
- 纵向 `padding`/`border` 按浏览器语义**不撑高行框**（与相邻行重叠），本轮照此实现，不是缺口。
