# Orilumn KMP+CMP 架构分层与共享边界

> 定位：**项目的共享边界总纲** —— 回答"哪些可以完全共享、哪些必须平台分开处理、现在哪里还分裂着"。
> 是所有整改方向（含 `平台一致性整改方案.md`）的母文档。
> 原则一句话：**凡非"OS 强制 / 真系统能力"的逻辑与渲染语义一律共享；平台壳只留进程入口 + expect/actual 接缝 + 打包。**

---

## 1. 分层总览

模块与依赖方向（单向，禁止回跳）：

```
┌─ 平台壳 ──────────────────────────────────────────────┐
│   app(MainActivity) / desktopApp(main) / （未来）iosApp │
└──────────────▲─────────────────────────────────────────┘
┌─ shared-ui ──┴─ CMP 共享 UI ───────────────────────────┐
│  书架 / 阅读面 / 设置 / 目录 / Snackbar / 亮度遮罩(ReaderLight) │
└──────────────▲─────────────────────────────────────────┘
┌─ engine-skia ┴─ 排版与绘制（android+jvm 同源码）──────────────┐
│  SkiaParagraphBreaker 断行 · LineWindowDrawer 行绘制             │
│  SkParagraphFactory 字体族/样式 · （待归位）图片解码               │
└──────────────▲─────────────────────────────────────────┘
┌─ common ─────┴─ KMP 纯逻辑库 ──────────────────────────┐
│  css 级联 / html+epub 解析 / 盒式流布局 / 分页 / 进度        │
│  settings / SQLDelight schema / 字体二进制解析           │
│  FontUploadServer(Ktor) · okio zip · 自研 XML · json      │
└────────────────────────────────────────────────────────┘
```

"半通用"能力已全部 KMP 化，不再有平台双实现：
- zip 读取 → okio；EPUB XML → 自研 mini XML DOM；HTML → Ksoup；JSON → kotlinx.serialization
- 数据库 → SQLDelight（schema 在 common）；文件选择 → mpfilepicker(FileKit)
- 字体上传服务器 → Ktor CIO（common `net/FontUploadServer`，S35 完成）

## 2. 可完全共享（100% 无平台代码，已成事实）

| 层 | 内容 | 说明 |
|---|---|---|
| common | CSS 层叠/`StyleComputer`、`BoxLayouter`/`NormalFlowLayout`、`Paginator`/`BreakAwareBookLayout`、`ListMarkers`、`TypographicProfile`、HTML/EPUB 解析、settings、SQLDelight schema、TTF/OTF `FontParser`、`net/FontUploadServer` | 单份 source |
| engine-skia | `SkiaParagraphBreaker`(ParagraphBreaker 实现)、`LineWindowDrawer`（按行窗口绝对 Y 绘制）、`SkParagraphFactory`（FontCollection/ParagraphStyle 唯一来源） | androidTarget+jvm 同源码 |
| shared-ui | 书架 `ShelfScreen`、阅读面 `ReaderScreen`、设置/目录面板、`ReaderLight` 亮度遮罩、Snackbar | CMP commonMain 单份 |

## 3. 必须平台分开（真边界，全项目收敛到这几处）

| 边界 | 接缝形态 | Android | Desktop (JVM) | （未来）iOS |
|---|---|---|---|---|
| 进程入口 | 壳 | `MainActivity` | `main()` | AppDelegate |
| 数据根路径 | `AppRoot` expect/actual（S30） | `filesDir` | `~/.orilumn` | NSDocumentDirectory |
| 日志 sink | `Logger` expect/actual | `util.Log` | 文件队列+print | os_log |
| 画布光栅化 | `ReaderPageRenderer` expect/actual | skia 离屏→Bitmap | 直接 skia Canvas | 视 CMP 目标 |
| 局域网 IP | `LanIp` expect/actual（S35） | `NetworkInterface` | `NetworkInterface` | getifaddrs/mDNS |
| **系统字体集合** | 平台 FontMgr | Android 系统字体 | macOS CoreText | iOS 系统字体 |
| 真系统能力 | 壳内 | 物理背光(WRITE_SETTINGS)、（可选）OpenGL 卷曲 | — | — |
| 打包发布 | 壳 | APK | DMG/icns | Xcode |

说明：

- **唯一的“同引擎排版却不同”的物理根源 = 系统字体集合（FontMgr）**。同一 CSS、同一引擎，字体度量随 OS 不同 → 断行位置略异，与 Chrome/Safari 排版差异同理。这是能力边界，不属工程分叉，不做像素级强求。
- 文件选择（mpfilepicker）、亮度遮罩（纯绘制）、字体加载（Skia FontCollection+okio）、WiFi 上传（Ktor）均已泛化成通用方案，**不再属于 expect/actual 接缝**。
- 结论：linux/windows/ios 未来**不会各搞一套引擎**——都是同一 common/engine-skia/shared-ui + 上表 tiny actual + 进程入口。

## 4. 现状整改面：该共享却仍然分裂

> 平台一致性整改（`平台一致性整改方案.md` Z/P/D/E/C/Q 系列）覆盖下述 A–F 全部整改面；
> 其排版子集（A/B）只是整体的一部分，C–D/E/F 属同一根因的更大整改。

| # | 面 | 平板现状（:app） | 桌面现状(:desktopApp) | 归属/进展 |
|---|---|---|---|---|
| A | 样式层（UA/主题/UI/链接色） | `assets/css/*.css` + android 加载器 | `DesktopReaderHost` 内联常量副本（已过时） | **Z 系列 Z1–Z4** |
| B | 绘制语义（每叶 x 偏移 / 列表 marker / 行窗口） | `BoxPageRenderer`（StaticLayout 绘制，含 xOff+marker） | `DrawLine`/`LineWindowDrawer`（缺 x、缺 marker） | **P 系列 P1–P3** |
| C | **阅读宿主/编排层**（增量分页、磁盘分页缓存、并发优先 P1–P14） | `BookDocumentController`(~1900行)+`BoxChapterLayouter` | `DesktopReaderHost` 简化版（无增量/无缓存） | 未共享（面最大） |
| D | **字体匹配/池** | `FontPairing`+`WeightedFontResolver`(Android Typeface) | `SkParagraphFactory.resolveFamilies`(Skia) | 应对齐 engine-skia |
| E | **图片解码**（封面/插图） | `BitmapFactory` | Skia Image（`DesktopShelfHost`/`DesktopImageBounds`） | 应统一 Skia（目标结构附录 A 已列） |
| F | 绘制宿主 | `BodyPageView`(Custom View) | 共享 `ReaderScreen` 已接入 | Q1 后退役 |
| G | 旧管线测试 | Robolectric 测真实 StaticLayout | — | Q1 后随 StaticLayout 退役 |

**根因判断**：A/B 之外的 C/D/E/F/G 是同一个根——**平板阅读面还没有进入 shared-ui + engine-skia**（G 阶段引擎 S24/S25 已完成，但平板壳仍跑旧 StaticLayout 管线；桌面反而最先消费新引擎）。因此：

- Z/P 系列先把**共享那份**做对（A/B），再让平板切过去（Q1），避免把已发现的错复制到平板上。
- Q1 完成后，C/D/E/F/G 坍缩：平板与桌面共用同一引擎 + 同一 `ReaderScreen`，仅剩 §3 真边界。

## 5. 建议路线（完整整改，按依赖排序）

| 序 | 事项 | 内容 | 对应 |
|---|---|---|---|
| 1 | 样式单源 | UA/主题/UI/链接色收进 common；删 assets 与内联副本 | Z1–Z4 |
| 2 | 绘制语义共享 | DrawLine 收 xLeft+marker；markerForLeaf 共用助手；桌面输出同位几何 | P1–P3 |
| 3 | 字体/图片收敛 | 字体池只产二进制给 Skia FontCollection；Typeface/WeightedFontResolver/BitmapFactory 退役 | D/E |
| 4 | 平板绘制侧 Skia 化 | `ParagraphShape/BoxPageRenderer/BodyPageView` → shared-ui `ReaderScreen`+`LineWindowDrawer`；`StaticLayoutBreaker` 与 `BookEngineSwitch` 退役 | Q1/S25+S31 |
| 5 | 编排层共享评估 | `BookDocumentController` 的增量/磁盘缓存/并发优先级策略（纯逻辑）评估平移进 common/engine-skia，桌面不再保留简化宿主；需单独论证磁盘缓存跨平台性 | C |

## 6. 验收口径

- `rg` 层面消灭 §4 表中所有"另一份实现"：样式、绘制、字体、图片、编排各剩 single source。
- 两端真书同设置跑同一引擎 + 同一 `ReaderScreen`；对比只含字体度量差异（§3 边界）。
- 全绿：`./gradlew :common:jvmTest :app:testDebugUnitTest :desktopApp:test :engine-skia:jvmTest :shared-ui:jvmTest`。
- 一步一 commit，文档随代码入库。
