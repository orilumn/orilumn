**「英文禁则」不需要新表。** 现有三张表里 ASCII 部分已覆盖：

### 0.2 「其他语言」的口子留在哪（关键：不扩接缝）

**接缝每次只为一个已确证的需求扩，不为推测扩。** 本轮的口子全部在**数据形状**上，一个参数都不加到断行器接口。

| 层 | 口子 | 现在 | 将来怎么接 |
|---|---|---|---|
| 数据 | 禁则表按语言组织的**值对象**（不是类里的 `const val`） | 中英合一的单表 | 拆成按语言选择的表 |
| 数据 | 每语言的 `lefthyphenmin` / `righthyphenmin` 随词典走 | en 的值（en 是 2/3，德法不是） | 加词典即带参数 |
| 数据 | 词典按语言组织，多本可同时装载 | 只有 `hyph-en-us` | 加 `hyph-fr` / `hyph-de` 即是加数据 |
| 签名 | `Hyphenator.hyphenate(text, lang)` | **`lang` 由调用方按 script 判定填入** | 判定源换成 `:lang()` / `dc:language` |

**英文断词本轮不需要 `lang` 参数。** 适用范围按 **script 判定**：只对**纯 ASCII 拉丁字母 token**
跑 K-L。于是中英混排的书里只有英文词被断，中文一个字不动，而断行器接口**零扩张**。

> ⚠ **已知局限（必须写进锁和文档）**：法语/德语/西班牙语也是拉丁 script，
> 会**误用** en-us 规则被断在非音节处（拉丁变音字母 ß é è 等不在 ASCII 白名单内，天然被排除）。
> 这比不断词**略差**，但远好于把英文词典套到中文上。将来精确化时改的是「怎么选出 lang」，
> **断点集与断行器接口都不用动**。

**现在就知道但不用做的一条**：书级语言目前是**零** —— EPUB `dc:language` 未解析、
`ComputedStyle` 无 `lang` 字段、`:lang()` 不支持（`HtmlTreeConverter.kt:190-193` 虽把 `lang`
/`xml:lang` 存进 attrs，但断在属性层，从未流到样式与排版层）。
另：`font_faces.lang` 是**字体表**的一列（跟着 `FontFace` 走），**语义未查证**，
但它**不是「书的语言」**，拿它判断词语言大概率是错的。

## 1. 架构落位（AGENTS.md 分层校验，先过这一关）

### 1.1 分层归属

| 新增/改动 | 所属层 | 理由 |

- `NormalFlowLayout`（排版层上）零改动
- `WhiteSpaceBreak.breakLeafLines` / `breakWrappedLines`（排版层上）零改动

- 回归面被压到「断行器实现 + 绘制器」两个文件，加上 `LineBreakSegments` 一张表

### 2.1 不动的（写死，任何步骤不得修改）

| 项 | 语义 |
|---|---|

| `DrawLine.range` | 同上 |

| `BrokenLine.heightPx` | `lineHeightPx(fontSizePx, lineHeightRatio)`，首/中/末行一致 |

依据：T0 已把两套下标的映射定死为 `skiaIndex = j + n(j)`（`j` = 行内叶文本相对下标，

`drawEmphasis:483`、`DrawLine` 的原子盒表字段。断行层不需要知道占位符存在。

### 2.2 S2 契约冻结 ✅ **已定案**（2026-09-30）

> 每条都附**已核实的事实**（S2 逐个读代码得到，不是推论）+ 理由 + 被否方案。
> **S3 起 `ParagraphBreaker` 签名不得再改。**

#### (a) 行内几何的载体：断行器**不产出**几何，Aligner 是独立纯函数 ✅

**已核实的事实**

| 事实 | 出处 |
|---|---|
| `BrokenLine` 只有 2 个字段 `(range, heightPx)`；接口 KDoc 明写「each carrying its char range into [text] and its height」 | `ParagraphBreaker.kt:142` |
| prepare 路径的**全部**消费者只读 range + heightPx | `NormalFlowLayout.kt:573/596/691/786`（盒流切割）、`ShapeGeometry.kt:113`（图高 / ruby 增量）、`BoxChapterLayouter.kt:2669/2692` |
| `ParagraphShapes.shapeOf` 同样只取断行结果，**行内样式明文交给绘制层** | `ParagraphShapes.kt` 类文档：「Run styling remains the drawing layer's job」 |
| 量画一致生死线只断言 range / yTop / yBottom / xLeft，**不断言行内字形位置** | `SkiaDrawLineWindowCoherenceTest` |
| `BrokenLine` 生产构造点 **7 处**（`WhiteSpaceBreak` 3 / `ShapeGeometry` **1** / `SkiaParagraphBreaker` 3），另有 20 处测试 fake | grep |

> ⚠ 原方案此处**漏了 `ShapeGeometry.kt:125`**（带 grown 高度 copy-construct），已补进上表。

**结论：prepare 阶段零 `x_i` 需求。** 断行只决定「哪些字符在哪一行」；行内几何是**绘制阶段**的事。

**定案**：`ParagraphBreaker` **零改动**（不扩 `BrokenLine`、不加参数）。
Aligner 是独立纯函数，**只在绘制时调用**（S5）。

> ⚠⚠ **更正原方案的一处伪代价。** 原 §2.2(a) 写「代价是 Aligner 要跑两次（prepare 一次定页切、
> 绘制一次定落位）→ 必须缓存（S6-3）」。上表证明 **prepare 从不调用 Aligner**，
> 所以 (a) 的代价是 **0**。S6-3 若做「断点/几何缓存」，理由只能是「翻页回看零成本」，
> **不得再引用这条已作废的「跑两次」**。

**被否方案 1：扩 `BrokenLine` 加 `slackPx` / `xOffsets`。** 四条理由：

1. **热路径白付内存与 GC** —— `BrokenLine` 在 prepare 里按行分配（章级 935 leaf），
   它带的几何在 prepare 里**永远读不到**。
2. **要跟着 hops 搬** —— `WhiteSpaceBreak.kt:97` 把 `range` 平移重建、`ShapeGeometry.kt:125`
   带 grown 高度 copy-construct；几何得跟着搬或重算，而这两处都不是断行器。
3. **把「量」写进「画」的契约** —— `breakLines` 的 KDoc 刻意只承诺 range + height，
   这条接缝存在的意义正是「S3 换实现而周边零改动」，塞进几何就毁掉它的最小性。
4. 20 处测试 fake 被迫跟随（默认值能免编译，但接口语义已被污染）。

**⚠ 随之冻结的两条实现约束（不写下来 S5 必踩）**

1. **同源**：Aligner 必须与断行器走**同一套量宽器 + 同一套字体解析路径**
   （S3 的 `SkiaRunMeasurer` + `SkiaFontPool.current()` 缓存单例 —— **教训 ⑩：两侧不同源，
   比值从 1.20x 虚高到 4.05x**）。
2. **分层**：Aligner **不能**接 `DrawLine`（那是 engine-skia 的渲染层类型，`common` 依赖它即越层）。
   它只接**原语**（`text` / `range` / `availWidthPx` / `justify` / 一个「逐字 advance 的取宽口」），
   由 engine-skia 在 S5 用 `DrawLine` 的 `rubyRuns` / `imgHidden` / `colorRuns` / `fontRuns` /
   `baselineShifts` 组装出那个取宽口。**断行器看不到这些行内数据、绘制侧看得到** ——
   这不是新问题，是既有设计（`DrawLine` KDoc 已注「占宽保守，字符流/断行不变」），S5 沿用即可。

> ⚠ **层级归属更正**：原 S4 把 Aligner 标为「排版层（上）」。按 AGENTS.md，Aligner 产出**字形 x 坐标**、
> 依赖**逐字 advance 度量**，属**渲染层（几何测量 / 分行控制）**；标点挤压是它内部的一条策略常量，
> 不改变归属。文件仍放 `common/laying/`（与 S1 的 `LineBreakSegments.kt` 同域）。

#### (b) 断点集形态：`BooleanArray` 承载的值对象 ✅

**已核实的事实 / 硬约束**

- 贪心填充需要**向前回溯**「≤ k 的最后一个断点」。逐字流式给不了回溯 —— 要么 O(n) 重扫，要么带隐式状态。
- **S7 自己的判据就要求它是可比较的值**：「新增锁：中文段 / 中英混排段**产出的断点集**与
  「不跑断词」时**逐值相同**」。流式产物写不出这个锁。
- S6-3 的缓存按 `(文本, 样式, 版心)` 命中，整段断点集是最自然的缓存单元。

**定案**：`class BreakOpportunitySet` 内部持 `BooleanArray(length)`，对外**只暴露**
`mark(i)` / `opportunityAt(i)` / `lastOpportunityAtOrBefore(i)` / `contentEquals`（供锁用）。
构造收 `List<BreakOpportunitySource>`（见下方「断点增强器」），**顺序无关**（都只往同一张表上打标）。

**被否方案**：① 裸 `BooleanArray` —— 无名字、无 `lastOpportunityAtOrBefore` 的单一入口，
S7 的锁只能整数组 `contentEquals`，diff 不可读；② 流式 —— 上面三条硬约束全不满足。

#### (c) `overflow-wrap` / `word-break` 不进签名 ✅（用户已拍板）

**已核实的事实**：F11/F12 **全项目零生产消费** ——
`ComputedStyle.overflowWrap` / `.wordBreak`（`ComputedStyle.kt:311/313`）只出现在级联
（`StyleComputer.kt:363-368`）与测试；`LongStringBreaker.breakOpportunities`
（`LongStringBreaker.kt:37`）只出现在自身单测。

**定案**：**不接线**。`breakLines` 三个重载**零扩张**。
R1 core = 「无可用断点且该单元放不下时，在任意字符处断开」= UAX#14 overflow 语义，
与 Skia/Chrome `overflow-wrap: normal` 同形。
与 `break-word` 的唯一区别在**是否影响 min-content 尺寸**，而 `minContentWidth` 已独立走
`minContentSegments`、不经过断行器 → 零影响。
**已记 TODO Q3**，接线列为与主链路解耦的独立后续项。

> ⚠ **R1 core 的行为规格（S1 实测钉下，S3 必须复刻）**：紧急态下**每个位置都算断点 + 贪心填满**，
> **不是「塞不下就溢出」**。实测 `abcd`（Roboto @20px）：`W=12/14/16/20` → 逐字一行；
> `W=24` → `ab·cd`；`W=40` → `abc·d`；`W=60` → 整段。即「能填几格填几格，填不下再断一格」。

#### T0 坐标约定与 4 处落点（抄进本文档，作为 S5 施工图）

```
skiaIndex = j + n(j)
```

`j` = 行内叶文本相对下标（`j = i - line.range.first`）；`n(j)` = 该位置之前的原子盒数，
由「行内原子盒起始相对下标」的有序表前缀计数 **O(1)** 得到。
**落点只允许 4 处**（判据，见测试计划 T0）：

1. `paintText` 构建段落时，把原子盒位置转成 `addPlaceholder`
2. `drawRuby:390` 的 `ps` / `pe`
3. `drawEmphasis:483` 的 `i`
4. `n(j)` 的计算与存储（`DrawLine` 的原子盒表字段）

**落点 4 的字段占位（本轮不加实现，只定名与语义）**

#### (d) 量宽器：逐码本 × 逐字形回退，**不整形** ✅ **S3 取证定案（T8）**

S2 冻结了「Aligner 与断行器同源」，但**没定同源的那个量宽器怎么测**。
S3 开工前必须量这件事 —— T0–T7 全在断点决策上，路线 B 的量宽地基从未验证过。
实测（`docs/自建断行引擎-测试计划.md` §T8，14 支探针全部已删）结论如下，**全部是实测不是推论**：

| # | 结论 | 关键数据 |
|---|---|---|
| 1 | `Σ逐码本 advance == 段落自然宽` | 最大 Δ **0.000015px**，含跨字面回退与代理对 |
| 2 | letterSpacing = **`Σadv + n·lsPx`**（n=码本数、**含末字符**） | `Δ/(n−1)` 列不是常数 → 排除 `(n−1)` 模型。实现上逐码本各加一次即可，零特判 |
| 3 | **必须逐码本解析字面**，不能整段一个面 | `[MySerif, STSong, serif]` 上整段单面 **Δ=+32.69px** |
| 4 | **遍历顺序：外层族栈、内层 manager**（= `FontCollection` 语义） | 写反了 `Δ=+49.5117px`；修正后 13 例中 11 例 **Δ=0.0000** |
| 5 | `matchFamiliesStyleCharacter` 对 `TypefaceFontProvider` **返 null** → 覆盖判定自建：`matchFamilyStyle` + 「glyph ≠ 0」 | 内嵌字体是生产真实路径（para 确实用内嵌面），这是 **P0** |
| 6 | `matchFamilyStyle(注册别名)` 返回的 `familyName` 是**字体自带名** | 缓存键**不能用 `familyName`**（跨字体撞键） |
| 7 | **CJK 零整形偏差** | 兰亭序 **84 字长串 Δ=+0.000000%**；汉字合字检测最小差 +0.0000 |
| 8 | **拉丁会丢 kern 与连字**（唯一的行为变更） | 连字只在 CJK 面（STSong `fi` **−9.00** @100px）；kern 只在拉丁面成规模（TNR 59 对 / Georgia **0 对**，最大 **−3.52**） |

**为什么「不整形」是对的而不是省事**：它同时是三处同源的自洽前提 ——
断行侧量 `Σ` 逐码本、S4 Aligner 的 `x_i = x_0 + Σ(w_j + delta_j)` 用同一个 `advanceOf`、
S5 逐字 `drawString` 落位（**每个 `drawString` 只含一个字符，Skia 无从整形**）。
三者同源即量画一致。反过来若量宽走 Paragraph 整形（单侧更准，教训 ⑳），就会与逐字绘制**双向失配**。

**这条路被四条实测堵死，不能靠绕**：
① skiko `Paragraph` **无任何字形/簇级位置查询**（`javap` 确认：只有反向的
`getGlyphPositionAtCoordinate` 与行级 `getLineMetrics`）→ 「整段整形一次 + 查每簇位置」不存在；
② kern 可以在 Aligner 里补（`w_j = adv_j + kern(cp_{j−1}, cp_j)`，两侧同表即自洽），
但**连字补不了**（它改变字形个数），而连字恰是 **CJK 面上更大的那个**（−9.00 vs −3.52）——
补一半要「每面 62×62=3844 次 Paragraph 测量建表」，覆盖小偏差、放过大偏差，投入产出不成立；
③ 全部整形缺口**都是负的**（整形只会更窄，15 个面 × 多组无一为正）→ S6 的「整段 paint」
只会比量出的窄、**不可能溢出版心**，这让 S6 从否决项变可选（教训 ㉑）；
④ CJK 语料下整形宽 == 逐码本宽（Δ=0.0000）→ **本项目主语料上两种绘制完全等价**。

**行为变更（对外可见，唯一一条）**：含拉丁字母的行**失去 kerning 与 fi/fl 连字**。
量级已量化（`fi` @STSong@100px = −9.00px），暴露面已量化（中文网文 ≈ 0；
`books/` 英文书 25–32 处/万字符）。**有意接受**（理由见 ②），登记 TODO Q5。

**回归锁的字体资产**：**不能用 woff2** —— 本测试环境下 woff2 面上
`getStringGlyphs`/`getUTF32Glyphs`/`getUTF32Glyph` **全返 0**（每个字母同一个 notdef 宽 17.734375），
且**段落自己也不使用它**（`families=["Roboto"]` 实测宽度 = 系统 Helvetica 的和）。
真 ttf/otf（`Georgia.ttf` / `Times New Roman.ttf` / `Helvetica.ttc` / `Arial Unicode.ttf`）上
`Σ逐码本 == Σ整段 == measureTextWidth` 全部成立 ⇒ woff2 是 CoreText+woff2 的测试环境特有（教训 ㉓）。

### S4 — Aligner（slack 分配 + 标点挤压）

**层**：**渲染层**（几何测量 / 分行控制）——⚠ 由 S2 更正，原标「排版层（上）」。
Aligner 产出字形 x 坐标、依赖逐字 advance 度量，按 AGENTS.md 属渲染层；标点挤压是它内部的
一条策略常量，不改变归属。文件仍放 `common/laying/`。

**新增**：`common/laying/LineAligner.kt` —— 纯函数。

**签名按 S2(a) 冻结的形状**（**不是**原方案的 `(text, range, naturalWidth, availWidth, measurer)`）：

```kotlin
// common（排版/渲染共享层）—— 只接原语，不接 engine-skia 的 DrawLine
class AlignedLine(val xOffsets: FloatArray, val slackUsed: Float)

object LineAligner {
    fun align(
        text: CharSequence,
        range: IntRange,
        advanceOf: (from: Int, to: Int) -> Float,  // 逐字 advance 的取宽口，engine-skia 侧组装
        availWidthPx: Float,
        justify: Boolean,                          // 末行/nowrap 行传 false
    ): AlignedLine
}
```

- **不接 `DrawLine`** —— 那是 engine-skia 类型，`common` 依赖它即越层（AGENTS.md 分层约束）。
  engine-skia 在 S5 用 `DrawLine` 的 `rubyRuns` / `imgHidden` / `colorRuns` / `fontRuns` /
  `baselineShifts` 组装出 `advanceOf`。
- **`advanceOf` 必须与断行器同源**（S3 的 `SkiaRunMeasurer` + `SkiaFontPool.current()` 缓存单例）——
  **教训 ⑩：两侧不同源，比值从 1.20x 虚高到 4.05x**。
- `justify=false` 时只算 `x_i` 不分配 slack，供 S6-1「无 slack 整段 paint」直接取用。

**内容**

1. **策略 A**（纯 CJK 逐字均摊）—— 照抄 T4b 测出的 Skia JUSTIFY 机制（slack 均摊到字形 advance），
   视觉将与现状**逐像素一致**。
2. **策略 B**（Latin-only 行按空格）—— T3b 实测策略 A 在纯英文行**完全无解**（0 CJK 槽 / 35 空格槽）。
3. **cap = 0.25em**，超出即放弃该行（T3 实测 p95 拉伸仅 1.35px = 0.030em，cap 远未被触碰）。
4. **零槽位/负 slack 行**：不做任何分配，原样绘制（T3 实测 0 例；结构上零槽位 = 整行一个长不可断单元 → R1 处置）。
5. **标点挤压**（路线 B 相对路线 S 的**独有**能力，`delta_j` 取负）：行尾标点压进版心。
   这是 S 路线结构性做不到的，必须在本步落地，否则 R4 只做了一半。
6. **末行不拉**（CSS 语义）。

**判据**

| 项 | 判据 | 依据 |
|---|---|---|
| 铺满精度 | 非末行右缘误差 max < 0.5px | T4 实测 JUSTIFY max −0.0002px；T3b 策略 B 残差 0.7px（肉眼不可见，需单列说明） |
| cap | >0.25em 的槽位 = 0 | T3 实测 0/13151 |
| 连字/kerning | 不破坏（`Σ逐字 == Σ逐字跨度 == 整段跨度`） | T3 已证本项目正文无连字压缩 |
| 首行缩进 | 不改变 slack | T3 实测「否」 |
| 末行 | 不拉 | CSS 语义 |
| 回归 | `JustifyStretchTest` 绿 | R3 既有锁 |
| 标点挤压 | 行尾禁则标点的右缘**不越版心**，且不破坏行内其它字间距 | 本项为新增能力，需新写锁 |

## 6. 明确不做

拆成三类，因为它们的**决策性质不同**，混在一张表里会让人误判优先级。

### 6.A 「不删」—— 东西保留，本轮不动

| 项 | 为什么 |
|---|---|
| `SkiaParagraphBreaker` | 两个活用途：① **T1 等价性对照的基线实现**（判据「假阴性 = 0」要拿它比，没基线就无法判）；② 回退开关。删了二者同时失效 |

### 6.B 「本轮不做」—— 范围外，有明确触发条件

| 项 | 为什么 | 什么时候回来 |
|---|---|---|
| **其他语言断词**（法/德/日…） | 本轮只英文（§0.1）。口子已留在**数据形状**上（§0.2 三条约束），加词典即加数据 | 用户需要 en 以外语言 / 要做精确到语言时 |
| **按语言选择禁则表** | 中文 + 英文共用一套表（§0.1），实测无冲突面。`KinsokuRules` 已收成值对象，选择点留好 | 出现 CJK 之外的、禁则规则与拉丁语系不同的语言（日文小書き文字等） |
| MathML 实际实现 | 本轮只回答「能不能承载」（T7 Q1–Q6 全通）与「坐标系怎么修」（T0） | R-F：`InlineItem` + 占位符插入 |
| Rust | 重评条件是「性能不达标**且**优化手段用尽」；T5e 实测章级 0.370x，判据 ≤1.5x **余量 4 倍** → 不触发。且绘制侧即使偏高也是 +ms/屏 级，不构成换语言的压力 | 性能判据真不达标时 |
| 断点/几何缓存 | **不是否决，是条件触发** —— 在 S6-3，排在「无 slack 整段 paint」「Latin 整段」之后 | S6 前两条做完仍超标 |

### 6.C 「有意否决」—— 做过了，结论是别做

| 项 | 为什么 |
|---|---|
| **相邻断点抑制规则** | 我给 K-L 加过，理由是「`algorithm` 应该是 `al-go-rithm` 而非 `al-g-o-rithm`」。实测一致率 **97.66% → 92.54%**，缺失点 3801 → 25099。TeX / pyphen **保留**相邻断点，`al-go-rithm` 是 prio 数组本身就只给 gap 2/4（**教训 ⑼**） |
| **F11 / F12 接线** | 三条理由见 §2.2(c)。核心：R1 core 已是 CSS `overflow-wrap: normal` 的语义，而 F12 的区别只在**是否影响 min-content 尺寸** —— `minContentWidth` 已独立走 `minContentSegments`，不经过断行器 |
| **`lang` 参数进 `ParagraphBreaker.breakLines`** | §0.2：本轮按 script 判定即可，**一个参数都不加到断行器接口**。将来真要接，也只接一个 `lang`，不连带 F11/F12 |
| **`—` 从 `NO_BREAK_BEFORE` 移出** | T2c 已否决：Skia 的 LB21b（`—\|—` 禁断）与「`—` 前后可断」冲突，移出反而制造假阴性。代价是 `填\|—` 上我们比 Skia 严（假阳性），**有意接受** |
