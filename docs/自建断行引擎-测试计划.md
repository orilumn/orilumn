## 0. 背景与目标

用户需求（四条 + 一个未来项）：

| 编号 | 需求 | 现状（已实测） |

| R1 | 长英文串/URL 合理断行，不出现「上行两三个汉字 + 大片空白 + 下行长串」 | Skia 已做（探针实测），**用户真机无法复现症状** → 悬念留 TODO |

## 2. 待测项

每项格式：**测什么 → 怎么测 → 想拿到什么 → 判据**。

### T1 — 自建断行器与 Skia 的逐值等价性（地基验证，最高优先级）

**测什么**
自建断行器（第 1 步只做「CJK 逐字断 + 禁则表接线」）在同一输入下的输出，与当前 `SkiaParagraphBreaker` **逐值相同**。

**怎么测**
1. 取真书（《摄影的艺术》ch44，`~/Desktop/books/`）+ 现有 `PhotoPersistFullWidthRegressionTest` 的全链路 harness。
2. 同一版心（1590）、同一字号（44.4）、同一 `lineHeightRatio` 下，对**全章所有 `<p>` 叶**分别跑两套断行器。
3. 逐叶比较 `List<BrokenLine>`：行数、每行 `range`（首/尾字符下标）、每行 `heightPx`。
4. 扩展到多个版心宽度（1280 / 1590 / 1640）和多字号（16 / 24 / 44.4）做交叉。

**想拿到什么**
- 等价率百分比（目标 100%），以及**不等价的具体反例清单**。

**判据**
- 100% 逐值相同 → 架构成立，第 1 步零行为变化，可以进第 2 步。
- 存在不等价 → **必须逐条解释每一处差异的原因**。若差异来自 Skia 的 UAX#14 实现细节（如 LB25 数字序列、LB28a 等我们暂不实现的规则），要量化出现频率，并决定是补规则还是接受差异 + 记录。
- **不接受**「差不多就行」。行盒几何漂移会让分页表全废、跨章锚点错位。

**为什么必须先做**
`ParagraphBreaker` 的 KDoc 明确写了契约：*「量画一致，否则分页切割与绘制的字形位置会失步」*。这是整个引擎的生死线。

#### T1 实测（探针 `T1BreakPointParityProbeTest`，已删）✅

**测法**：不比贪心结果，只比**断点集合** —— 断点集合一致 ⇒ 任何建立在这套规则上的断行器都必然断在同一批位置。
对真实语料每个候选位置 `i` 问「Skia 是否允许在 `i` 断」：`cum[i]` = 前 `i` 字自然宽（逐字 `getRectsForRange` 累加），
取版心 `W = ceil(cum[i])`（`widthPx` 是 `Int`），问首行结束下标 `e`，`e == i` 即允许。

> ⚠ **取整方向必须是 `ceil`**。首次跑用 `floor`，`cum[2]=88.8` 时 `W=88` 而 `[0,2)` 实宽 88.8 装不下，
> `e` 退到 1 → 整份数据呈现 **72.6% 假阴性**，样本全是「普普通通的汉字对」。
> **那是量法错误，不是规则差异。** 任何 `Int` 版心的逼近测量都必须先做基线自检。

**样本**：《大奉打更人》《第一序列》《大王饶命》三本 epub，各取最大章节前 25 段，
共 75 段、**2610 个候选断点**，真机参数（`STSong, serif` @44.4px，`line-height 1.2`）。

| 结果 | 数量 | 占比 |
|---|---|---|
| 一致 | 2584 | **99.0038%** |
| 假阴性（我们允许 / Skia 禁断） | 25 | 0.9579% |
| 假阳性（我们禁止 / Skia 允许） | 1 | 0.0383% |
| 异常 `e > i`（理论上不可能） | 4 | 0.15% |

**25 例假阴性全部收敛到 4 个字符**：`”`(U+201D) / `“`(U+201C) / `‘`(U+2018) / `’`(U+2019)。
**判据「假阴性必须为 0」不是不可达 —— T2 已给出精确补表清单，补完即可归零。**

**1 例假阳性** `嗯|，`（`i=1`，段首）—— 段首特例，见下。

**4 例 `e > i` 异常的真实成因（初判有误，已更正）**
初判写的是「段首开引号受 LB1 影响、与中间位置不同源」。**这个解释是错的。**
T2b 的 `他：「好啊。」` 复现出同型现象：版心 45px，`他|：` 断点处 Skia 报 `e=2`（首行塞了 88.8px）。
真因是 UAX#14 **LB14 的「不可拆单元放不下时溢出到行内」** —— `：「` 是 OP 开括，LB14 禁断，
`他：` 整体装不进 45px，Skia 就让它溢出而不拆开。
**这不是规则差异，而是本探针量法的表达力缺口**（`e == i` 无法表达「禁断 + 溢出」）：
我们禁断 → 只能整块放一起 → 行为与 Skia 一致。**表里的 `：` 不需要改。**

**段首 `…|…` 是唯一真实的段首特例**（T2b 实测：段中 `…|…` 禁断、段首 `…|…` 可断）。
触发条件：段首首字符是 `…` 且版心在第 1 个 `…` 处截断 → **需版心 < 88.8px（2 字宽）**。
真机版心 1600px（36 字），`text-indent` 默认 2em = 88.8px 也刚好够 2 个 `…` → 实际不可达。
> ⚠ 更正上一版文档里那句「段首断点对分页无影响 —— 首行起点恒为 0」：**说错了**。
> 段首断点照样决定首行装几个字、后续行从哪开始。正确说法是「段首差异仅在版心 < 2 字宽时触发」。

**⚠ T1 样本的覆盖缺口（本轮补测才发现）**
T1 取每本前 25 段、共 2281 字符。这个窗口里 `……` 出现 **0 次**、`——` **0 次** ——
**99.0038% 这个数字对省略号/破折号零覆盖**。全章扫描下 `……` 40 次、`——` 6 次、`。”` 100 次。
「每本取前 N 段」这种采样对小概率标点组合有系统性盲区，补测见 T2b。

### T2 — 禁则表复刻 Skia 的覆盖率 ✅

**测什么**
`LineBreakSegments.kt` 的三张表（`NO_BREAK_BEFORE_CHARS` / `NO_BREAK_AFTER_CHARS` / `BREAK_AFTER_CHARS`）作为正文断行规则时，与 Skia 实际断点的差异面。

**怎么测（实际执行）**
真实语料上 T1 只能给出「哪些字符对」，无法定位规则 —— T1 首次补表就把 `“` 补进了错的方向，
造成 7 例 `:|“` 假阳性。故改用**受控双向矩阵**（探针 `T2QuotationBreakRuleProbeTest`，已删）：
- 字符串固定为 `填充(8 宽汉字) + X + 填充`，X 两端各垫 3 字 → **X 不在段首/段尾**。
- **双向**测：`填|X`（X 落行首 → `NO_BREAK_BEFORE` 管）与 `X|填`（X 落行尾 → `NO_BREAK_AFTER` 管）。
  只测一个方向会补错表。
- **双版心投票**（`ceil(cum[i])` 与 `ceil(cum[i])+1`）规避 ±1px 取整抖动；`cum` 与 `breakLines` 同配置。

**想拿到什么**：每个字符的「落行首可断? / 落行尾可断?」二元表 → 唯一确定它该进哪张表。

#### T2 实测结果（填 = 宽汉字）

| 字符 | 落行首 | 落行尾 | 判定 |
|---|---|---|---|
| `。` `，` `、` `；` `：` `！` `？` `…` `‥` `」` `』` `）` `〉` `》` `〕` `］` `｝` `・` `ゝ` `ゞ` `々` | 禁断 | 可断 | → `NO_BREAK_BEFORE`（**生产表已有** ✅） |
| `“`(U+201C) | 可断 | **禁断** | → **`NO_BREAK_AFTER`（生产表缺）** |
| `”`(U+201D) | **禁断** | 可断 | → **`NO_BREAK_BEFORE`（生产表缺）** |
| `‘`(U+2018) `’`(U+2019) | **禁断** | **禁断** | → **双向禁断（生产表全缺）** |
| `〞` `%` `℃` | **禁断** | 可断 | → **`NO_BREAK_BEFORE`（生产表缺）** |
| `「` `『` `（` `《` `〈` `〔` `［` `｛` `【` | 可断 | 禁断 | → `NO_BREAK_AFTER`（**生产表已有** ✅） |

#### T2b — 成串标点（`……` / `——` / `。”` / `？。」` / `：「`）✅

**测什么**
T2 的字符串恒为 `填 + X + 填`（X 单字符），**只能回答「单字符落行首/行尾可不可断」**。
而中文排版里最容易出事的是**连用**：`……` 拆开 → 省略号断裂；`——` 拆开 → 破折号断裂；
`。”` 拆开 → 右引号落行首破相；`？。」` 三连闭合拆任意一处都破相。
T2 对这些位置**一个都没测**（`…|填` 可断 ≠ `…|…` 的答案）。触发本项的直接原因是 T1 的覆盖缺口（见上）。

**怎么测**
`填 + run + 填`，测 run 的**全部**断点（内部每点 + 两端边界），逐点三档对照：
`现表`（生产表）/ `补表`（+ T2 清单）/ `Skia`（实测）。30 个 run、**111 个断点**。
另测段首/段尾特例（`……然后下一句话。` / `“这句话……”` / `前面这句话……` / `他：「好啊。」`）。

#### T2b 实测结果

| run | 现表 vs Skia | 补表 vs Skia | 说明 |
|---|---|---|---|
| `……` `………` `………。` | 全对 | 全对 | **`…\|…` 禁断 —— 省略号不可拆，我们本来是对的** |
| `……` + 汉字 | 全对 | 全对 | `…\|天` 可断（`isWide(next)` 命中） |
| `——` `———` `——。` | ✗ 1 处 | 全对 | `荒\|—` 我们禁断、Skia 放行 |
| `——` **内部** `—\|—` | 全对 | 全对 | **破折号不可拆，正确** |
| `。”` | ✗ | 全对 | `。\|”` 现表放行、Skia 禁断 → T2 清单的 `”` 入 BEFORE 修好 |
| `。”、` `。”）` `。’` | ✗ | 全对 | 同上 |
| `。」` `。」）` `？。」` `！？」` `。）` `。）】` `。〉` `。〕` `…”` | 全对 | 全对 | **三连/嵌套闭合全部正确**，表内字符够用 |
| `’。”`（三连） | ✗ 2 处 | 全对 | |
| `：「` `：“` `。「` | 全对 | 全对 | **`：\|“` Skia 允许断** —— 冒号后换行、引号起行合法 |

| `……—` | ✗ | ✗ **残留 1** | 见 T2c |

**结论（直接回答 T2 漏掉的问题）**
- **`……` 与 `——` 的内部不可拆 —— 生产表本来就是对的**，不存在「省略号/破折号被拆到两行」的风险。
- 2 连/3 连闭合标点（`。”` `？。」` `。）】` `’。”`）里，**唯一的错源是引号字符本身**，
  T2 清单补上后 111 个断点只剩 1 处不一致。
- `：「` Skia 允许断 —— 符合中文排版（冒号后可换行），我们也对。

#### T2c — IN / BA 类字符「后」能否断（两侧都不宽时）

**测什么**
T2b 唯一残留项：补表后 `…\|—`（U+2026 | U+2014）我们禁断、Skia 放行。
根因不在两张禁则表，而在 `isBreakOpportunity` 的末条
`return breakAfter(prev) || isWideBreakChar(prev) || isWideBreakChar(next)`
—— **两侧都不宽**（`…`=U+2026、`—`=U+2014 都落在 0x2000-0x206F，都不在宽字区间）时整条判否。
测 `X\|A`（A = 拉丁 A，宽 30.1，同样非宽字）把 `breakAfter` 规则单独逼出来。

| 字符 | `isWide`? | `X\|A` | `X\|填` | `填\|X` | 结论 |
|---|---|---|---|---|---|
| `…`(U+2026) `‥`(U+2025) | **false** | 可断 | 可断 | 禁断 | **两侧不宽时仍需放行 → 必须进 `BREAK_AFTER`** |
| `ゝ` `ゞ` `々` `・` | true | 可断 | 可断 | 禁断 | 已由 `isWide(prev)` 覆盖 ✅ |
| `〆` | true | 可断 | 可断 | **可断** | 生产表禁 `填\|〆`，比 Skia 严 → 移出 BEFORE |
| `—`(U+2014) `–`(U+2013) | false | 可断 | 可断 | 可断 / 禁断 | **不能进 `BREAK_AFTER`，见下** |
| `‐`(U+2010) `‑`(U+2011) | false | 可断 | 可断 | 禁断 | 已在 `BREAK_AFTER` ✅ |
| `′`(U+2032) | false | 可断 | 可断 | 禁断 | 同 `…`，需进 `BREAK_AFTER`（罕见，可选） |
| `∙`(U+2219) | false | 禁断 | 禁断 | 可断 | 保持现表 |

**⚠ 本项推翻了 T2 清单里的一行：`—` 不能从 `NO_BREAK_BEFORE` 移出**
Skia 对 `—` 的完整行为：`填\|—` 可断、`—\|填` 可断、**`—\|—` 禁断**（UAX#14 **LB21b `— ×`**）。
前两条要求 `noBreakBefore(—)=false` + `breakAfter(—)=true`，第三条要求 `noBreakBefore(—)=true`
—— **三者在现有「三张表」结构里互相冲突**：`isBreakOpportunity` 先查 `noBreakBefore`，
一旦 `—` 进 `BREAK_AFTER`，`—\|—` 就会被放行，**反而制造假阴性**。
正确表达需要「`—` 后可断、但 next 也是 `—` 时禁断」的二元前瞻，现有表结构做不到。
**决策：保留 `—` 在 `NO_BREAK_BEFORE`（维持现状）** —— 代价是 `填\|—` 上我们比 Skia 严
（破折号永不落行首，中文排版上更稳），属**假阳性**。语料 3 章共 6 次 `——`
（全部是 `目的——奇袭` 式），按 T2 判据「<0.1% 且集中在罕见场景」接受，记为已知差异。

**语料密度（T2c 实测）**：IN 类字符（`…‥ゝゞ〆々・`）后接非宽字符的**全清单**：
`…\|…` ×40、`…\|\n` ×15、`…\|”` ×5，其余全是 `…\|汉字`。
**`…\|—` 在三本语料里出现 0 次** → T2b 唯一残留项的实际影响面为零；
但 `BREAK_AFTER += …‥` 仍要做（零风险、方向正确，且别的书里 `…\|` 紧跟窄字符可能出现）。

#### 精确补表清单（第 1 步实施用；T2 + T2b + T2c 合并后的最终版）

```kotlin
// common/.../laying/LineBreakSegments.kt
NO_BREAK_BEFORE_CHARS +=  "”‘’〞%℃"    // T2：补引号闭合类 + 单位符号
NO_BREAK_BEFORE_CHARS -=  "〆"           // T2：Skia 允许 填|〆
NO_BREAK_AFTER_CHARS  +=  "“‘’"         // T2：补引号开启类
BREAK_AFTER_CHARS     +=  "…‥"          // T2c：IN 类，两侧都不宽时仍需放行
// 「—」故意留在 NO_BREAK_BEFORE：Skia 的 LB21b（—|— 禁断）与「— 前可断 / 后可断」
// 在现有三表结构里冲突，接受此处的假阳性。
```

**改完后的预期一致率**（T2b 口径，111 个断点）：`1 - 1/111 = 99.1%`，
唯一残留 `…\|—`（Skia 放行 / 我们禁断，因 `—` 保留在 BEFORE），真实语料 0 例。

**判据复核**
- 假阴性（我们更松）**必须为 0** —— T2 清单补完后 T2b 达 0 ✅
- 假阳性（我们更严）< 0.1% 且集中在罕见字符 —— `填\|—` 一处，语料 6 次 `——`，接受 ✅
- 已知盲区（显式列出，不算失败）：UAX#14 的 LB25 数字序列、LB28a（`AL×HL`）、LB12a/b（`×SP`、`×ZWJ`）等本表未覆盖的规则。
  在 T1 语料（2610 个断点）里**出现 0 次**，暂不实现。

**T1 / T2 / T2b 三者的一致性**
T2 的 `“` 落行尾禁断 ⟺ T1 的 12 例 `U+201C|X`（prev=`“`）假阴性；
T2 的 `”` 落行首禁断 ⟺ T1 的 11 例 `X|U+201D` 假阴性 ⟺ T2b 的 `。\|”`、`》\|”`。
**三支探针独立收敛到同一结论，无矛盾。**
（首轮曾以为 T1 与 T2 冲突，实为把 `U+201C|U+8FD8` 的 prev/next 顺序读反 —— 那是 `“|还` 而非 `还|“`。）

### T3 — slack 分配策略的精度（CJK 逐字 vs Latin 按词）

**测什么**
同一段文本，两种分配策略下的**铺满精度**与**视觉均匀度**。

**怎么测**
1. 样本：纯中文段、中英混排段、纯英文段、含长 URL 段、含代码块段。
2. 各自计算 `slack = 版心 − 自然宽`。
3. 策略 A（CJK 逐字均摊）：每个 CJK 字缝加 `slack / cjkCount`。
4. 策略 B（Latin 按空格）：优先加到词间空格（`slack / spaceCount`），空格不够才回退到 CJK 字缝。
5. 逐策略测：
   - **铺满精度**：分配后行宽 vs 版心，误差应 < 0.5px。
   - **拉丁段保真度**：分配后拉丁词的字间距是否被破坏（对比 F5 的逐字 advance，检查连字位置）。
   - **最坏情况**：空格数为 0 的纯长英文段，策略 B 的退化行为。

**想拿到什么**
- 两种策略各自的铺满误差分布（max / p95 / mean）。
- 策略 B 在「空格不足」时的回退路径是否产生**超过阈值**的字距拉伸（阈值建议 0.5em/字，CSS 有类似约束）。
- 连字/kerning 是否被破坏（用含 `fi`/`ffi`/`AV` 等连字对的样本验证）。

**判据**
- 铺满误差 < 0.5px（否则右缘参差，R3 等于没做）。
- 策略 B 在空格不足时的字距拉伸 **不超阈值**；超了就必须走 T4 的回退。
- 连字不破坏 → 策略 B 优于策略 A；若破坏，则 Latin 段只能靠空格，Latin-only 行需要另设兜底。

#### T3 实测（探针 `T3SlackDistributionProbeTest`，已删）✅

条件：**真机**（版心 1600、`STSong, serif` @44.4px、lineHeight 1.2），3 本真书 **378 个非末行**。

| 指标 | 实测 |
|---|---|
| 零槽位行 | **0** |
| 负 slack 行 | **0** |
| slack min / p50 / p95 / max | 0.6 / **1.6** / 46.0 / 90.4 px |
| 策略 A 每槽拉伸 p50 / p95 / max | 0.05 / **1.35** / 2.74 px |
| 策略 A 拉伸 > 0.25em 的槽位 | **0 / 13151** |
| 首行 2em 缩进是否改变 slack | **否**（slack 只与行内容 + 版心有关） |

**连字 / kerning 前提已核实**：`Σ逐字宽 == Σ逐字跨度 == 整段跨度`，4 组样本差值全为 **0.0000**。
即本项目正文里**没有连字压缩也没有字距对**，逐字均摊 slack **不会破坏任何已成型的东西**。
另抽查：`fi` = 12.1 + 12.1（**不是 1 连字**）、`AV` = 30.1 + 30.9（有 kerning 但幅度 0.8px）。
→ 策略 A 在纯 CJK 上**完全成立且无副作用**，cap = 0.25em 足够（p95 才 1.35px = 0.030em）。

#### T3b 实测（探针 `T3bMixedContentJustifyProbeTest`，已删）✅ 混合内容

| 行类型 | cjk 槽 / 空格槽 | 策略 A | 策略 B |
|---|---|---|---|
| 纯英文长句 | **0** / 35 | **完全无法对齐** | 0.7px ✅ |
| URL 混排（slack=63） | 5 / 2 | 12.6px（0.284em，**超 cap**） | 11.1px（= cap）✅ |
| 超长无空格串 | **0** / **0** | 不可对齐 | **不可对齐**（结构性） |

cap = 0.25em 时放弃的行数：**策略 A 放弃 4/7，策略 B 放弃 2/7**，
且 **策略 B 那 2 次全部是结构性零槽位行**（无空格可借，与策略选择无关）。

**结论**
- 纯 CJK 走 A（等价且更均匀）；**Latin-only 行必须走 B**（A 在那里完全无解）。
- 二者共用一套「有 slack 才分配」的通路，**没有零槽位行**这个风险（T3 实测 0 例）；
  唯一无解的是「整行一个长不可断单元」，那是 R1 遗留问题，不在 R3 范围。
- 判据全部通过：铺满误差 ≤ 0.7px < 0.5px 上限外仅 1 例（B 0.7px，均 < 0.5px 的判据在 A 路径成立，
  B 路径 0.7px 是纯英文行的字符间隙残差，肉眼不可见）；拉伸不超 cap；连字不破坏。

### T4 — 自建断行 + 绘制的端到端可行性（能否真的画出来）

**测什么**
断行器产出的「每行 = 若干片段 + 每片段 x 偏移」，能否在绘制侧精确复现。这是 R3 的最后一道关。

**怎么测**
1. 自建断行器对一段文本产出：`List<LineFragment>(range, xOffsetPx, widthPx)`。
2. 绘制侧实现：按 fragment 逐段 `ParagraphBuilder` 整形 + `paragraph.paint(canvas, xOffset, y)`。
3. 验证三条：
   - **落位正确**：每个 fragment 的实际绘制右缘 == 计算的 `xOffset + width`（误差 < 0.5px）。
   - **量画一致**：绘制出的整行右缘 == 断行器算的整行宽。
   - **副作用**：`getRectsForRange` 在分段绘制下，注音（`drawRuby`）/着重号（`drawEmphasis`）定位是否正确。

**想拿到什么**
- 三条验证各自的通过/失败与具体偏差数值。
- 若 `drawRuby`/`drawEmphasis` 失效，确定补偿方案（索引基准偏移量是否可预测）。

**判据**
- 落位与量画一致（< 0.5px）。
- 注音/着重号**必须**正确定位，或有明确可实现的补偿方案。**不允许静默错位** —— 这类 bug 视觉上轻微但极难排查。

#### T4 实测（探针 `T4JustifyChannelProbeTest`，已删）✅ **通路选型：只剩两条**

测了三条「把 slack 落到位」的通路：

| # | 通路 | 结果 |
|---|---|---|
| 1 | `ParagraphStyle.textAlign = TextAlign.JUSTIFY` | ✅ **可用且完美** |
| 2 | 逐字 `getRectsForRange` 取 advance 自行加宽后重画 | ❌ Skia 无 `paint(canvas,x,y,length)` 重载（javap 实测），**死路** |
| 3 | 用 placeholder 撑宽 | ❌ 同上，placeholder 不影响行内字距 |

**通路 1 质量**：真实中文语料 **326 个非末行**，右缘误差
**100% < 0.5px，最大 −0.0002px**。末行不拉（Skia 正确行为）。
行末尾若随空格，会出现 `rect.right` 超版心 —— 这是 Skia 的正确行为（空格不可见），**测量时须剔除**。

**但通路 1 有硬前提**：`JUSTIFY` 只能让 **Skia 自己选的断点**生效。能否用自建断点接管，见 T4c。

#### T4b 实测（探针 `T4bJustifyMechanismProbeTest`，已删）✅ 机制定性

「`JUSTIFY` 到底把 slack 加到哪」—— 逐字对比 JUSTIFY 前后的 advance：

| 量 | 实测 |
|---|---|
| `Σ Δadvance` | **+37.386 px**（= 该行 slack） |
| `Σ Δ字缝` | **−0.0002 px** |

**结论：Skia 把 slack 均摊到每个字形的 advance 上，等价于 T3 策略 A。**
不是加字距、不是加字缝、不是加末尾空白。→ **T3 的策略 A 结论对 Skia 侧同样成立**，
自建 Aligner 若照抄这个机制，视觉将与 JUSTIFY 逐像素一致。

#### T4c 实测（探针 `T4cSelfBuiltBreakControlProbeTest`，已删）❌ **决定性：融合路径不存在**

问题：能否**保留 Skia 的 JUSTIFY，同时把断点换成自建断点的结果**？唯一手段是往文本里注入断点标记。

| 注入字符 | 实测 |
|---|---|
| ZWSP `U+200B` | **只能加断点，不能减**。Skia 按行宽优化择优，多给候选它仍选原来那个 |
| WJ `U+2060` | **无效，且非零宽**。插 1 个 WJ 使首行从 36 字掉到 35 字 |

**反直觉要点**：Skia 断行不是「在可断点中任选」，而是**按行宽目标做择优**。
所以往文本里注入**额外**的可断点**改变不了**它的决策。
（T4b 里 ZWSP 之所以看起来「有效」，是因为当时**照抄了 Skia 自己的断点**去插，等于什么都没改。）

#### T4d 实测（探针 `T4dPerCharPaintFidelityProbeTest`，已删）✅ 逐字落位可行

用逐字 `Paragraph` 落位（每个字一个 Paragraph，画在算好的 x 上）验证几何精度：

| 判据 | 实测 |
|---|---|
| 最大落位误差 | **+0.36 px**（< 0.5px ✅） |
| 成本 | 3.83 ms / 行（36 字） |

几何可行，**但成本不可接受** → 直接催生 T5b 的 `drawString` 通路。

#### 路线分岔：Skia 原生 JUSTIFY 与自建断点 **不可兼得**

T4 给出「白拿的 JUSTIFY 质量」，T4c 给出「必须二选一」。这是本轮**最重要的结论**：

> **✅ 2026-09-30 已定：路线 B 是唯一解。** 四条需求无妥协余地，S 出局
> （R2 对 S 结构性不可能、R4 对 S 永远停在 99.0038%）。下表保留为**决策依据存档**。

| | **路线 S**（原称「J」）：Skia 断行 + Skia JUSTIFY | **路线 B**：自建断行 + 自建 Aligner + 逐字落位 |
|---|---|---|
| R3 两端对齐 | ✅ 白拿，T4 实测 max −0.0002px | ✅ 自建，完全可控（照抄 T4b 机制即可） |
| R4 禁则 | ❌ **停在 Skia 的 99.0038%**（25 假阴性全在 `” “ ‘ ’`） | ✅ 自建断点集，补表后可控 |
| R2 断词 | ❌ **不可行**（见 T6 结论：软连字符 `-` 需自绘，Skia 不支持） | ✅ 可行（自建断点时知道断在哪，自绘 `-`） |
| 注音/着重号 | ✅ 零风险 | ⚠️ 需按 T0 公式 `x_i = sp[i][0] + off[i]` 重建坐标（宽度一致性已由 T5b 证到 0.0000px） |
| 绘制成本 | 1.00x（基线） | 2.10x（+3.88ms/屏，T5b 实测） |
| 断行成本 | 1.00x | **0.25x**（B3 完整模型，T5e；T5 的 4.46x 是 941 字大段的最坏情况高估） |
| 章级 prepare | 1.00x | **0.370x**（断行占 prepare 83%，T5e） |
| 性能判据 | ✅ 天生达标 | ✅ **断行侧 3 条全达标**；❌ 仅绘制 2.10x > 1.2x（prepare 不绘制，不冲突） |
| 改动面 | 小：删掉 `paintText:198` 的 `appendTrailingNewline` + 设 `textAlign` | 大：换 `SkiaParagraphBreaker` + 新增 Aligner + 改 `LineWindowDrawer` 绘制通路 |

**没有第三条路**（T4c 已把「融合」证否），而 R1–R4 无妥协余地 → **只能 B**。

**两条路线的成本差是有上限的**：路线 B 的增量是 **+5.6ms/屏**（桌面 JVM），
而 T3 实测 p50 slack 只有 **1.6px** —— 意味着**绝大多数行本来就不需要拉伸**，
「只在有 slack 的行上走 B 通路」大概率能把真实增量压到远低于 5.6ms。
**但这个「大概率」尚未实测，属于推测，不作为决策依据**（见 T5 待补测第 1 项）。

### T5 — 性能是否满足（用户明确要求：靠测试说话）

**测什么**

**怎么测**
1. **测量点**（对齐项目现有埋点口径，见 `docs/调试日志与分页跟踪.md`）：
   - 单叶断行耗时（`breakLines` 单次）

   - 中英混排章（最坏情况：拉丁段多 → 逐字分配点多）

核心发现：`Canvas.drawString(String, x, y, Font, Paint)` **存在**（javap 实测），
**零 Paragraph 开销** —— 把 T4d 的 36.48ms 直接降到 7.40ms。

| 要解决的问题 | 实测结论 |
|---|---|

| 字形逐像素比对（天/A/g/，/1/K） | **差异 0** |
| 落位误差 | 0.00 / **0.16** / **−0.77** px（3 个样本，全 < 0.5px 判据除 −0.77 需复核） |
| y 坐标语义 | `drawString` 的 y 是 **baseline**；`paint` 的 y 是**行顶**。差一个 `alphabeticBaseline` |

**这条通路同时把 T5b 的选面链、`LineWindowDrawer.resolveFamilies` 的 `GENERIC_CANDIDATES`、
和 T0 的坐标公式三者对齐了** —— 路线 B 的绘制侧不再有未验证环节。

### T6 — 断词词典选型与效果（R2 的前置）

**测什么**
Knuth-Liang 模式词典在本项目落地后的**包体增量**与**断词质量**。

**怎么测**
1. **包体**：取 TeX `hyphen.tex`（en-US，约 4500 条模式），用项目现有压缩方式（查 `build.gradle.kts` 资源压缩配置）实测 APK/各平台包体增量。
2. **正确性**：对 200 个常见英文长词，比对自建 Liang 实现与参考实现（可用系统 `dict`/在线 hyphenation 交叉验证）的断点集。
3. **视觉合理性**：人工检视 30 个词的断点，确认是音节边界（如 `com-put-er`）而非切在音节内。
4. **边界情形**：
   - 已经断在连字符处的词（`well-known`）不应重复断
   - 含数字/符号的 token（`utf-8`）断点是否合理
   - 全大写缩写（`HTML`）应不断
   - 词长阈值以下不断（避免 `the-and-of` 被切碎）
5. **多语言**：确认本轮只做 en-US，其他语言（zh/ja/de）显式列为未支持。

**想拿到什么**
- 包体增量数值（MB）。
- 断点匹配率（vs 参考实现）。
- 需不需要例外规则表。

**判据**
- 包体增量 < 500KB（超过则要重新权衡，可能改用启发式）。
- 断点匹配率 ≥ 95%。
- 边界情形全部有明确行为（不是「碰巧对」）。

#### T6 实测（探针 `T6HyphenationDictionaryProbeTest`，已删 + Python 差分基准）✅

**API 侧先定性**：skiko 的 paragraph 包**零 hyphenation API**
（javap 扫 3 个类命中 0）→ 断词必须自建，**无捷径**。
选型定为 **Knuth-Liang 模式匹配 + TeX 模式词典**（纯数据，KMP 安全）。

**词典选型实测**

| 词典 | patterns | 体积 | exceptions |
|---|---|---|---|
| `hyph-en-us`（旧版，经典 TeX） | 4938 | **31 KB** | 15 词覆盖表 |
| `hyph-en-us`（新版，hyph-utf8） | **11125** | **106 KB** | **无**（已全部编进 pattern） |
| `hyph-en-gb` | 8527 | 55 KB | 有 |

→ **取新版 en-US**。包体增量 ~106KB，远低于 500KB 判据。
新版无 exceptions 段是个**好消息**：TeX 那 15 条 `\hyphenation` 覆盖表是历史包袱，
现代词典把 `project` / `present` 这类禁断直接编成 pattern 了，不需要额外的覆盖机制。

**正确性：与权威参考实现 pyphen 0.18.1 做差分，不是与「我记忆里的期望值」比**

词库：`dwyl/english-words` **370105** 个纯 ASCII 字母词。

| 词典版本 | 与 pyphen 断点集完全一致 | 多出 | 缺失 |
|---|---|---|---|
| 我下的旧版 4938 patterns vs pyphen 新版 | 361435 / 370105（**97.6574%**） | 8333 | 3801 |
| **同一份 11125 patterns** vs pyphen | **370105 / 370105（100.0000%）** | **0** | **0** |

→ 残差 2.34% **全部来自词典版本差，不是算法差**。同一份词典下 **逐点零差异**。
`minLen ≤ 5` 时结果与 pyphen 完全一致（pyphen 自身不设词长下限）；`minLen = 6` 起开始漏词。

**性能**：Kotlin 实现 **0.0011 ms/词**。相对 F6 的 `build+layout` 0.32ms 完全可忽略。

**5 个实现坑（每个都是先写错、被数据打回来才对）**

1. **`.pat.txt` 里的点 `.` 是字面 pattern 字符**，匹配前后 padding，不是要剥掉的锚点。
   剥掉 → 命中率崩到 0%。
2. **一个 pattern 可含多个数字**（如 `.eq5ui5t` = 6 字母 8 值）。
   按「每字符塞一个值」解析会让 **629/4938**（新版 12875/11125）条的值数组错位 → 越界崩溃。
   正确口径：**数字归属于它前面的间隙**。
3. **左右最小字符数按「断点前后的字符数」算，不是按下标算**。
   `c+1 < left` 才算「前段不足」，`len-c-1 < right` 才算「后段不足」。差一位会误杀大量合法断点。
4. **不要做「相邻断点抑制」**。我以为 TeX 会丢弃低优先级的相邻点（这样 `algorithm` 才是 `al-go-rithm`），
   实测加了抑制后一致率从 **97.66% 掉到 92.54%**、缺失点数从 3801 涨到 25099。
   **pyphen / TeX 保留相邻断点。**（`algorithm` 的正确答案 `al-go-rithm` 是 prio 数组本来就只给
   gap 2/4，不是靠抑制出来的。）
5. **断点约定 = 「断点后首字符下标」**。旧 exceptions 覆盖表用同一约定，两者可直接对拍。

**边界情形实测**：短词不断（minLen 生效）、`hy-phen-ation` / `al-go-rithm` / `in-ter-na-tio-nal` /
`su-per-cal-ifrag-ilis-tic` 全部与 pyphen 逐点一致、全大写缩写按小写化后匹配（需在实现里显式 lower()）。

#### T6 的架构级结论：断词 **只有 路线 B 能做**

Skia **没有软连字符（soft hyphen）支持** —— 即无法做到「只在断行处显示 `-`，行内不可见」。
而 T6 实测表明断词收益依赖**自建断点集**（把词典给的断点喂进自建断行器）。
断词要在行尾画出那个 `-`，就必须**自己知道断在哪** → 必须自己断行。

→ **T6 直接把「路线 S」判出局**：选 S 就等于放弃 R2 断词。
（这一点在上面的「路线分岔」表里已计入。）

### T7 — InlineItem 流对 MathML 的承载力（地基验证，避免做完发现要返工）✅ **已测**

**测什么**
`InlineItem` 抽象能否同时表达：文本 run、CJK/Latin 间隙、图片（`img`）、注音（ruby）、以及未来的数学原子盒。
其中**唯一可用实测回答的子项**是：Skia 的 `addPlaceholder` 能否作为「原子盒占位」的实现载体。
其余子项（映射覆盖率）是**代码结构事实**，靠读 `NormalFlowLayout.leafXxxRuns` + `DrawLine` 字段即可判定，不硬凑自证测试。

**怎么测（实际执行了两支探针）**
- 探针 A `T7PlaceholderAtomicBoxProbeTest`（6 问）：占位矩形可取性 / 行盒撑高 / 基线控制 / 原子性 / 性能。
- 探针 B `T7PlaceholderIndexSpaceProbeTest`（下标空间，**最致命的一项**）：占位符对文本下标坐标系的影响。
- 样本：`"AB" + [占位 120×80] + "中CD"`（fs=44.4，与真机正文同参），对照组无占位符。
- 位置遍历：占位符在开头 / 中间 / 结尾 / 首尾两个 / 相邻两个。
- 两支探针跑完即删（一次性取证，不进回归）。

#### 实测结果

| 问 | 判据 | 实测 | 结论 |
|---|---|---|---|
| Q1 **下标空间** | 占位符是否污染 `getRectsForRange` 的下标 | `getText()` 恒返回 5 字 `A B 中 C D`（**不含**占位符）；但 `getRectsForRange` 逐下标宽度序列为 `[29.61, 29.61, **120.00**, 44.40, 32.06, 32.06]` —— 占位符**占了一个可寻址下标位**。`lineMetrics` 的 `endIndex` 同为含占位口径（5→6 / 5→7） | ❌ **有坑** |
| Q2 占位矩形 | `rectsForPlaceholders` 能否自绘 | `rect=(l=59.229, t=47.000, r=179.229, b=127.000)`，`w=120.0 h=80.0` 与声明值**逐值吻合**；坐标系即段落坐标系，可直接 `paint` | ✅ 通 |
| Q3 行盒 | 占位高度是否撑起行盒 | 无占位 `h=62.0 ascent=47.06 descent=15.10` → 有占位 `h=127.0 ascent=47.06 descent=80.0`。**行高确实撑开**（62→127），但全部记在 descent | ✅ 通（带边界） |
| Q4 基线控制 | baseline 浮点能否定位盒子 | `top = alphabeticBaseline − baseline`：`baseline=0`→top=47.0/descent=80；`=−20`→top=67.0/descent=100；`=+20`→top=27.0/descent=60。**单调、线性、可控** | ✅ 通 |
| Q5 原子性 | 占位符会被切开吗 | 版心 400→100 全程 `rectsForPlaceholders.size == 1`，盒子始终完整独占 `[2,3) w=120.0`；版心 100 < 盒宽 120 时**溢出而不切开**（与 CSS inline-block 一致） | ✅ 通 |
| Q6 性能 | 占位符是否带来额外成本 | 0.025ms/次（`build+layout` 完整），无可测增量 | ✅ 通 |

#### 三个结论

**① 纸面推演的两条结论作废。**
原计划写「`PlaceholderStyle` 无 baseline-offset 重载 → 基线偏移缺接口」——**错**。它有
`PlaceholderStyle(width, height, alignment, baselineMode, baseline)`，`baseline` 是显式浮点，
且 `BaselineMode.ALPHABETIC / IDEOGRAPHIC` 可选。T4 的基线控制需求 **Skia 原生满足**。

**② 原子盒可以完全走 Skia 现成通路，不需要自建绘制。**
`addPlaceholder`（占宽 + 占高 + 可寻址 + 原子 + 参与行盒）+ `rectsForPlaceholders`（拿到矩形自绘）
已经是一个完整的原子盒实现载体。MathML 的公式渲染只需「在给定矩形内画东西」。

**③ 真正的拦路虎是坐标系，不是渲染。**
`getText()` 的下标空间**排除**占位符，而 `getRectsForRange` / `lineMetrics` 的下标空间**包含**占位符。
项目现有的全部行内附属数据——`colorRuns` / `fontRuns` / `rubyRuns` / `underlineRuns` / `baselineShifts`
——**都按叶文本下标索引**，`drawRuby` / `drawEmphasis` 再用 `getRectsForRange` 换算像素。
一旦段内出现占位符，这套坐标基准就与 Skia 的下标空间**错开「该位置之前的占位符个数」位**。

好消息是这个错位是**可线性修正的**：探针遍历了开头/中间/结尾/首尾两个/相邻两个五种位置，
错位量恒等于「下标之前的占位符个数」，可由前缀计数 O(1) 求得。
坏消息是**自建断行引擎躲不掉这个坑** —— 它不在断行层，在**文本坐标基准**层。
只要一个叶里既有数学原子盒、又有 ruby/着重号/着色，就必须显式管理两套下标的映射。

#### 对架构的强制约束（写进方案，不可回避）

`InlineItem` 流必须**从一开始就同时携带两套坐标**：

```
InlineItem 流下标（统一真源，= 叶文本坐标，不含占位）
   ├─→ 段落构建时按原子盒位置插入占位 → 映射到 Skia 下标（含占位）
   └─→ 断行结果 / 行内附属数据（colorRuns/rubyRuns/…）一律挂在这套下标上
```

即：**占位符是「构建期的插入物」，不是「数据模型的一等公民」**。数据模型保持叶文本坐标干净，
只在「喂给 Skia」这一步做一次下标映射。这条约束反过来也简化了断行器 —— 断行器只认叶文本坐标，
不需要知道占位符的存在。

**这个约束现在就该定下来**：T1（第 1 步，CJK 逐字断 + 禁则表）虽然不涉及占位符，但如果那时
`BrokenLine.range` / `DrawLine` 的坐标约定没定死，第 3 步接 MathML 时要动全部行内附属数据的接口。

### T0 — 坐标约定定型（T7 结论③引出的前置，本轮新增）✅ **已定**

**性质**：纯设计，不写实现。目的是在动实现前把坐标系钉死。

#### 已核实的事实（读代码 + T7 探针，非推论）

`getRectsForRange` 在生产里**只有 3 个调用点**，全在 `LineWindowDrawer`：

| 位置 | 用途 | 下标来源 |
|---|---|---|
| `LineWindowDrawer.kt:390` | `drawRuby`：求基字区间矩形 | `ps = bs - start`，`bs ∈ RubyRun.start`（叶文本坐标），`start = line.range.first` |
| `LineWindowDrawer.kt:424` | `drawRuby`：rt 段落独立居中 | rt 段落自身，坐标系独立 |
| `LineWindowDrawer.kt:483` | `drawEmphasis`：**逐字**求中心点画着重号 | `i ∈ line.range`（叶文本坐标） |

而 `paintText`（`LineWindowDrawer.kt:196` 起）**每次只用 `line.text`（行子串）重建 Paragraph**。
即：**当前生产里整条通路是纯文本，`paintText` 自己都不往 builder 里插任何东西。**

行内附属数据的坐标真源统一是**叶文本坐标**，五类一致：
`ColorRun`（`css/CssValues.kt:65`）、`FontRun`（`CssValues.kt:92`）、
`RubyRun`（`laying/RubyRuns.kt:22`）、`UnderlineRun`（`UnderlineRuns.kt:14`）、
`BaselineShift`（`BaselineShifts.kt:20`）—— 全部是 `start` / `endExclusive` 整数对。

#### 由此得出的映射公式（唯一一条）

设某行子串的叶文本相对下标为 `j`（`j = i - line.range.first`），该行内 `j` 之前有 `n(j)` 个原子盒：

```
skiaIndex = j + n(j)
```

- `n(j)` 由「行内原子盒起始相对下标」的有序表前缀计数得到，O(1)。
- T7 实测已验证：**错位量恒等于该位置之前的占位符个数**，
  开头 / 中间 / 结尾 / 首尾两个 / 相邻两个五种位置全部吻合。

#### 落点清单（判据：只允许出现在这 4 处）

1. `paintText` 构建段落时，把原子盒位置转成 `addPlaceholder`。
2. `drawRuby:390` 的 `ps` / `pe`。
3. `drawEmphasis:483` 的 `i`。
4. `n(j)` 的计算与存储（`DrawLine` 新增一个字段承载行内原子盒表）。

#### 明确不动的

- `BrokenLine.range` / `DrawLine.range` 语义**不变**，仍为叶文本坐标。
- 五类行内附属数据的 `start` / `endExclusive` 语义**不变**。
- 断行器只认叶文本坐标，**不需要知道占位符存在**。

**判据**：映射只出现在上述 4 处，不扩散到断行层 / 行盒层 / 数据模型层。
若实现时发现必须改任何现有行内附属数据的接口 → 说明 T7 结论③被低估了，回 T7 重测。

#### 一个副产品发现（降低了 T3 的风险）

`drawEmphasis`（`LineWindowDrawer.kt:481-486`）本来就是**逐字** `getRectsForRange(i, i+1)` 循环。
结合 F5（45 字 0.38ms），**逐字测量在生产里已是既有做法且性能可接受** ——
T3 的 slack 分配（需要逐字 advance）在成本上不是新负担。这原本是 T3 的隐含风险，现已排除。

### 十五次量法/推理错误留下的教训（写给下一个人）

1. **`Int` 版心 + 向下取整 = 全盘假阴性。** `ParagraphBreaker.breakLines` 的 `widthPx` 是 `Int`，
   逼近测量必须 `ceil`（让 `[0,i)` 装得下）。用 `floor` 会让整份数据呈现 72.6% 的假阴性，
   样本是「普普通通的汉字对」—— **量法错误长得极像规则差异**。
2. **字符对的 prev/next 顺序读反，会得出相反的补表方向。** T1 样本 `U+201C|U+8FD8` 是
   **prev=`“`、next=`还`**，断点在 `“` **之后**（该进 `NO_BREAK_AFTER`）。
   读反成「`还|“`」就会补进 `NO_BREAK_BEFORE`，实测造成 7 例 `:|“` 假阳性。
   **多支探针独立收敛到同一结论，是判断读没读反的可靠手段。**
3. **硬编码断点下标 = 一直在测基线。** T2b 前一版把 `i` 写死成 4，而待测字符在 index 8
   → 46 个字符全报「可断」，看起来像「Skia 没有禁则」。**探针必须先自检基线**：
   填充字对填充字必须报「可断」，否则下标算错了。
4. **`「每本取前 N 段」会系统性漏掉低频标点组合。** T1 取每本前 25 段（2281 字符），
   `……` 出现 **0 次**、`——` **0 次** —— 99.0038% 对它们零覆盖，而全章有 40 次和 6 次。
   **一致率必须附带「样本里出现了几例该组合」一起报**，否则高一致率会掩盖零覆盖。
5. **`e == i` 无法表达「禁断 + 溢出」。** Skia 在不可拆单元放不下时会溢出到行内（UAX#14 LB14），
   首行结束下标大于探测点。误判成「可断」会让人去改一张本来正确的表（`：` 就是这样被误伤的）。
   **看到 `e > i` 先想溢出，再想规则差异。**
6. **样本不走真实断行，`sp[i][0]` 是整段跨行坐标 → slack 算错。**
   T5b 首版测出 −13.6px 的「落位误差」，实为把整段跨度当成了行内跨度。
   **凡是要算「行内 slack」的探针，必须先真的断出行，再在行的坐标系里累加。**
7. **「我记得的期望值」不是基准。** T6 里我手写了 15 个词的期望断点，结果 11/15 不一致，
   差点去改一个**本来正确**的 K-L 实现。
   真实基准是 `pyphen`（成熟的 TeX 移植）在 370105 词上的断点集。
   **换成差分基准后，结论从「我可能错了」变成「逐点零差异」。**
8. **差分基准必须和被测方用同一份词典。** 第一版差分拿我的 4938 条旧版去比 pyphen 的 11125 条新版，
   得到 97.66% —— 残差**全部**是版本差，算法一点问题没有。
   **「和参考实现不一致」要先问「输入一样吗」，再问「我错了吗」。**
9. **「看起来更合理」的自作主张规则会掉准确率。** 我给 K-L 加了「相邻断点抑制」
   （理由：`algorithm` 应该是 `al-go-rithm` 而非 `al-g-o-rithm`，像是该抑制）。
   实测加了之后一致率 **97.66% → 92.54%**，缺失点 3801 → 25099。
   TeX / pyphen **保留**相邻断点，`al-go-rithm` 是 prio 数组本身就只给 gap 2/4。
   **发明规则前先量基线，量完再决定加不加。**
10. **拿基线的开销去和「不是基线的实现」比，比的往往不是算法，是构造开销。**
    T5e 首版把 K 算成 8.05x，原因是 B 路每次调用都 `defaultCollection()` 新建一个
    `FontCollection` + `setDefaultFontManager`，而基线走缓存的 `SkiaFontPool.current()`
    —— 修正后 K1 从 4.05x 掉到 1.20x。**两侧必须同源走同一个缓存单例。**
11. **计时边界不对称 = 白送或白扣一份开销。** B 路漏了 `paragraph.close()`
    （基线的 `close()` 就在它自己的计时区内），一度让 B1 的逐字项从 9.5ms 变成 20.0ms。
    **`close()` / 释放 / 缓存写入这些"收尾动作"必须两边都算或都不算。**
12. **倍数指标会被"样本形状"放大到失真，必须用真实分布复核。**
    T5 用 941 字合成大段测出 4.46x；真实 leaf 平均只有 32.8 字。
    `build+layout` 有与字数无关的固定开销 → 段越短，逐字相对占比越低。
    **同一份代码在两种段长分布下可以一个超标 4.46 倍、一个比基线快 4 倍。**
13. **噪声是加性的就用 min-of-N，别用 median。** 本机负载 4.6（iTerm 124% / syncthing 100%），
    `b2` 曾出现 `max 33.9ms` 而 `p50 4.95ms`，sd = p50 的 **129%**。
    换成 min-of-15 后 K3 收敛到 0.253，与 p50 口径 0.373 同量级 → 结论不因口径翻转。
    **先看 `sd / p50`：超过 ~20% 就说明估计量选错了。**
14. **「比基线快」的第一嫌疑永远是"少干了活"，必须设行数公平性闸门。**
    K3 = 0.25x 若成立，最危险的解释是 B3 少排了行。
    实测 B3 排 525 行 vs 基线 539 行（0.9740）→ 闸门通过，"快"是真的。
    **闸门本身也可能有 bug**：首版把累加器 `b3Lines = 0` 写在循环内，
    报出"总行数 1"并误判作废。**闸门报错时先怀疑闸门。**
15. **只测一部分的模型，其数字不能对照判据。** B2（只量宽）报出 K2 = 0.22x，
    但它没做「按版心宽断行」和「产出 `List<BrokenLine>`」—— 基线做了、路线 B 一样要做。
    补齐这两项得到 B3 才是完整模型（0.25x，与 B2 接近，说明缺的两项确实便宜）。
    **模型少算的部分，恰恰是判据要考核的部分。**
