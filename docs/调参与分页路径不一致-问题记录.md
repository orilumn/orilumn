# 调参与分页路径不一致-问题记录

## 问题概述

在调参数重排时，**只有当前章**的章标题（h2）与正文之间的距离是正确的，**其他所有章**都是错误的。

观察到：同一个 CSS 规则在两种不同分页路径下渲染出两种效果。这不是 CSS 层叠优先级的问题，而是**分页计算路径不同导致的排版计算上下文差异**。

## 问题 1：TEMP 生命周期 vs「离开本章立即切换到磁盘表」的时机不一致

### 规则（分页调度总则 §1）

> “一旦使用临时表，在本章内就始终使用临时表，直到翻回章开头时，若本章磁盘表已就绪，则立即切换到磁盘表（不使用临时表先显示，直接显示磁盘表对应页面），抛弃本章临时表；离开本章时，本章临时表立即废弃。”

### 现状（代码）

- **调参关面板时的当前章**：通过 `startAnchorStream()` 创建 `InProgressPagination`（TEMP 会话），前台直接展示 `tempRenderLayout` 和 TEMP 页（`PathKind.TEMP`）。
- **注释（BookDocumentController，约 2560 行）：**  
  `The anchor-temp pages remain the live pagination for the whole session — the canonical (correct line-level) table is only activated when the reader reaches the chapter head / crosses chapters, via [finalizeTempOnLeave]. The current page is never re-rendered mid-chapter, so the temp↔canonical boundary cannot produce an in-place redraw or flash.`
- **触发时机**：`finalizeTempOnLeave()` 只在**跨章边界/离开本章**时触发，并非在「翻回章内其他位置」时触发。

### 矛盾点

「翻回章开头时，若本章磁盘表已就绪，则立即切换到磁盘表」是**本章内**的边界条件。而当前代码只在跨章时才调用 `finalizeTempOnLeave()`，**没有覆盖「回到章首（仍在本章内）」这个 case**。

这很可能是导致「回到本章还是停留在 TEMP 会话」的直接原因。

### 待验证

- 检查 `finalizeTempOnLeave()` 的所有调用点，确认是否需要扩展到指针到达章首/页 0（本章内边界）时也触发。
- 明确「离开本章」在翻页逻辑中的定义（跨章翻页时才算离开？还是翻到章首再翻上一页也需考虑？）。

## 问题 2：调参后旧的磁盘表为什么不删除？

### 现状

- 磁盘表按 `paramHash` 命名：`cache.file("book_$bookId", unit.chapterIndex, paramHash)`。
- 参数变化（LayoutParamKey 改变）→ 新 `paramHash` → 新文件名。**旧文件从未主动删除**，代码中未发现 `delete`/`remove`/`expire` 等清理逻辑。
- 读取时始终使用 `currentParamHash()` 去查找缓存文件。
- `ChapterUnit.invalidateForParam(newHash)` 保证：当 hash 不匹配时，内存中的 `paginationTable` 会被立刻清空，不会复用旧表。
- 因此**正确性是有保障的**。

### 问题

- 老文件成为**孤儿缓存（orphaned cache files）**，只增不删。
- 多次调参、切换排版主题、改变视口尺寸等操作会持续堆积大量旧版本磁盘表，导致**存储膨胀**。
- 这是**缓存生命周期管理缺失**，而非正确性缺陷。

### 建议

需要补充磁盘表清理策略：
- 当参数变化导致新 hash 生成时，清理该书本该章（或全书）**低于当前版本 epoch/早于本次 relayout 的旧 hash** 对应的磁盘表文件。
- 或者增加**LRU/容量上限**清理（如超过 N 个历史版本自动清理最旧的）。
- 至少在**切换书籍、彻底重排（invalidateAllLayouts）等大规模失效时机**考虑批量清理。

## 问题 3：B2 的意义与「翻到页面才知道磁盘表过期」的理解澄清

### 误解

前期推断认为：「要翻到对应页面才知道磁盘表过期再重排章节」是个问题。

### 正确认识

- **失效判定是即时的（访问时强制校验）**：`ensureChapterLayout()` 在相关分支都会先调用 `unit.invalidateForParam(currentParamHash())`（见 745、787 行）。只要参数已变化（hash 不同），无论是否翻页到该章，下次**访问**该章时，内存中的旧表都会被立刻清空。
- **磁盘文件读取也按当前 hash**：`buildLayout()`/`prewarmChapterBody()` 都用 `currentParamHash()` 去查找磁盘缓存文件。旧 hash 的文件根本读不到，等价于「找不到匹配当前参数的磁盘表」。
- **B2 的真正意义是预热（降低未来导航延迟）**：`requestWholeBookRelayout()` 派发的后台任务（PRIO_B2_CHAPTER）是为了**在新参数下，为其他章预先计算整章 canonical 分页表并写入磁盘（新 hash）**。
  - 如果 B2 已经跑完某章并写入新表，当用户翻到该章时，`buildLayout()` 能走 disk-hit 分支，用**增量窗口（WIN）**仅排目标页，首屏延迟远低于整章 `fullLayout`。
  - 如果 B2 还没跑完就翻过去，则磁盘无新表 → 走 `fullLayout`（FULL 路径）当场排全章。这是**安全的降级（correctness-first）**，而非设计缺陷。

因此 B2 的价值是**后台预排以减少将来访问时的排版延时**，而**不是**决定磁盘表是否过期。磁盘表的过期判定早已通过 `paramHash` 在访问路径上强制生效。

## 问题 4：TEMP vs FULL/WIN 路径导致的渲染不一致（核心）

### 路径差异

调参关面板关闭（参数真的变化）时：

1. **当前章（正确的那一章）→ TEMP 路径**
   - 走 `prepareRelayout()`，当前章**不**调用 `invalidateLayout()`。
   - 对大章（`light.totalBlocks > SMALL_CHAPTER_BLOCKS`）调用 `startAnchorStream()`。
   - 创建 `InProgressPagination`（TEMP 会话），前台同步排出**锚点页**（anchor-anchored 临时排版），直接展示 `tempRenderLayout`。
   - `pathMarker = PathKind.TEMP`。此刻展示的是**刚用新参数算出的临时流页面**。

2. **其他章（错误的章）→ 首次访问时多半走 FULL 路径**
   - `prepareRelayout()` 对非当前章全部 `invalidateLayout()`，清空 `paginationTable`、`layout`、`pageSlices`、`inProgress`、`paramHash = -1L`。
   - `requestWholeBookRelayout()` 将其他章提交到 B2 后台排版（异步）。
   - 用户翻页到某章 A 时，`ensureChapterLayout()` 发现 `laidOut=false` 且无表 → 走 `buildLayout()`。
   - `buildLayout()` 用当前（新）`paramHash` 查磁盘：若 B2 尚未执行到该章，新表未写入 → `cached == null`。
   - 进入非 disk-hit 分支：用 `boxLayouter.prepare()`（heavy prepare，全章级联+盒树全量）+ `boxLayouter.fullLayout()`（**整章全量排版，从章首开始**）计算整章切片，`bind` 后 `pathMarker = PathKind.FULL`。

### 原因分析

两条路径都使用**完全相同的排版参数（profile）**、**完全相同的 CSS 层（UA/author/theme/settings/UI）**、**完全相同的 StyleComputer（paragraphScale/gapScale 来自 profile）**。按理说每个盒的 margin/padding/line-height 等计算结果应该一致。

但实际出现「同一 CSS 规则，两种渲染效果」：

- **TEMP 路径（当前章）**：是**锚点锚定（anchor-anchored）**的临时流排版。它只针对锚点页及其周边用增量方式排版（`shapeTempPageForward/Backward`），且展示的是 `tempRenderLayout`。排版的“视角”和页切分的触发点是**锚点页**。
- **FULL 路径（其他章首次无表）**：是**整章从章首开始**的全量 canonical 式排版（`fullLayout`）。排版顺序、页切分边界的确定方式、以及在某些与前后盒折叠（margin collapse）、容器边界相关的上下文计算，可能与**仅排锚点页**的临时流在细节上存在路径差异。

**核心结论：渲染不一致是「TEMP」vs「FULL（首次无表）」这两种排版路径本身的实现差异导致的，而不是 CSS 层叠本身的错误。**

## 问题 5：章节排版中间产物是否及时丢弃？

### 现象关联

「章标题-正文间距」这种垂直间距的差异，极有可能与**排版中间产物的复用/残留**有关。特别是：

- 当前章用 TEMP 路径排版时，可能复用了某些上一次排版（旧参数）计算出的**中间结构**（如盒树缓存、容器 span、块间距缓存等）。
- 其他章用 FULL 路径时，是全新从头计算，没走到那些复用分支，导致计算结果不同。

### 代码线索（待核对）

| 位置 | 说明 |
|---|---|
| `ChapterUnit.prepareResult` | 全章 prepare 产物（cascade + box geometry + leaf extraction）。`invalidateLayout()` 会清空 `prepareResult = null`。但 `bindPrepare()` 在何时调用？是否在参数变化时总是重新生成？ |
| `ChapterUnit.structureCache` | **Typography-independent** 的块结构（leaf set + global char starts）。注释明确：`Survives typography changes (not cleared by invalidateLayout())`，只在结构性输入（cssBundle/useOriginalStyle/viewport 相关）变化时自我校验。若结构未变但排版参数变化时仍保留，是否会影响某些依赖它的计算？ |
| `ChapterUnit.blockShapeCache` | 每个块的 `ParagraphShapeRef`，按 layout-parameter cycle 缓存。`invalidateLayout()` 会 `blockShapeCache = null`。TEMP 会话期间如何维护？ |
| `ChapterUnit.pageCache`（disk-path 用） | 页级 assembled 产品。`invalidateLayout()` 会清空。 |
| `ChapterUnit.linkRangeCache` | 链接范围缓存。`invalidateLayout()` 会清空。 |
| `BoxChapterLayouter` 的 `prepareLight`/`prepare` | 是否总是基于最新的 `profile`（新参数）重新计算？`structureCache` 的复用是否会导致某些派生值“陈旧”？ |
| `StyleComputer` 构造 | 每次排版都会用新参数（`paragraphScale`、`gapScale`、`profile`）新建 `StyleComputer`。中间产物不应残留旧 scale。 |

### 核心疑点

1. **`structureCache` 的存活范围是否过宽？**  
   它故意**不随排版参数变化而清空**（注释：survives typography changes），目的是在拖动滑块（行距/段间距等）时复用叶子集合、char starts 等结构信息以提升性能。但这套结构是否真的**完全与排版参数无关**？  
   如果某些计算在构建盒树或推导容器 span 时隐含地依赖了旧的排版上下文，而又误用了 `structureCache` 的结果，就可能导致边界算错。

2. **TEMP 路径 vs FULL 路径对中间产物的取用方式不同**  
   - `startAnchorStream` 用的是 `prepareLight(markup, ..., unit.structureCache, ...)`（传入 structureCache）。
   - 首次无表走 FULL 路径时，`buildLayout` 里常用 `prepare` 或 `prepareLight`？需核对：`buildLayout` 非 disk-hit 分支（910+）用的是 `boxLayouter.prepare(...)`（heavy prepare），而不是直接复用 `prepareLight` 的结果。  
   两种 prepare 的实现细节、是否读取同一套缓存，是否有“只在 light 路径才更新某缓存”的逻辑，都值得排查。

3. **`invalidateLayout()` 是否真正覆盖了「排版计算过程」中所有会受新参数影响的临时状态？**  
   已知会清空：`layout`、`pageSlices`、`prepareResult`、`paginationTable`、`inProgress`、`tempRenderLayout`、`blockShapeCache`、`pageCache`、`linkRangeCache`、`linkRangeKey`、`shapedPageFrom/To`、`pathMarker`、`paramHash`。  
   但 `structureCache`、`markup`、`cssBundle`、`title` 等**结构性**字段**刻意保留**。这套设计本身是合理的（性能考量）。问题是：是否存在**本该随排版参数变化而失效，却被误判为结构无关而长期保留**的中间状态？

4. **`prepareResult` 的时效性**  
   `bindPrepare()` 将 prepare 结果与 `paramHash` 绑定。`invalidateForParam()` 只在 hash 不同时清空全套，但在某些路径（尤其是参数刚变化时的 TEMP 路径）是否有直接复用旧 `paramHash` 的 `prepareResult`？  
   如果 `prepareLight`/`prepare` 的某个调用点在**未校验 paramHash** 的情况下复用了 `unit.prepareResult`，就可能用到旧参数下计算的盒树细节。

### 建议排查方向

- 对比调参前后，同一章在**TEMP 路径**和**FULL 路径**下，`prepareLight` 的入参（尤其是 `structureCache` 内容是否一致）及返回结果差异。
- 检查 `structureCache.key` 的组成：它校验的是哪些字段？是否真的只包含「结构性」输入（DOM 结构、CSS bundle、useOriginalStyle、viewport 等），而**不包含**任何影响垂直间距的排版参数（lineSpacing、firstLineIndentEm、paragraphSpacingScale、paragraphGapScale、字体相关等）。
- 追踪 `startAnchorStream` 内部对 `prepare`/`prepareLight` 的调用链：是否存在复用 `unit.prepareResult` 的分支？以及复用时是否有 `paramHash` 匹配校验。
- 在调参关面板关闭后的首个落位（当前章 TEMP）和首个翻到其他章（FULL）这两个时刻，打印关键中间量：如每个块的 computed margin、container spans、首个叶子到标题的垂直距离等，直接对比数值差异。

## 补充（2026-10-07 修改后）

**问题 2 处理（本轮落地）：**

清理统一收口为 `BookDocumentController` 两个方法，全部按 `LayoutParamKey` 指纹判定：

- `cleanStaleDiskTables()` —— **指纹真变才动磁盘**：指纹偏离基线（构造时钉底、每次清理后推进）才删除全书**旧指纹**磁盘表（`PaginationCacheStore.cleanStaleParams`，纯文件名过滤 `<章>_<hash>.bin`），同指纹历史表保留（参数回退即命中）；指纹一致是空操作。内容感知而非全清：`setViewport`/`finalizeRelayoutAll` 的旧 `cleanBookAll` 全清也改走本入口。
- `cleanAllDiskTables()` —— 字体集合变更（导入/系统字体变更）后的全清兜底：字体度量不进 `LayoutParamKey`（键只含族名/字重锚点），指纹清理抓不到同指纹旧表，几何已旧必须全删。

**调用点（参数稳定点）：**

| 时机 | 入口 | 语义 |
|---|---|---|
| 面板关闭且排版指纹真变 | `finalizeRelayoutAll` → `cleanStaleDiskTables` | 门控已保证指纹真变，守卫恒过 |
| 视口变化（旋转/窗口调整） | `setViewport` → `cleanStaleDiskTables` | 指纹必变（内容盒在边距补偿下恰不变时旧表仍有效，不删才对） |
| 平板轻刷新节流循环收口 | `ReaderActivity.scheduleRelayout` 末尾 → `cleanStaleDiskTables` | 覆**面板外提交**：开书探针回填、原书设置提交、字体回退、夜间切换等 |
| 桌面两段式第二段 | `DesktopReaderHost.commitRelayout` → `cleanStaleDiskTables` | 覆桌面面板外提交（含开书探针回填） |
| 字体集合真变（`refreshSkiaFonts()==true`） | `ReaderActivity.refreshFontsAndRelayout` → `cleanAllDiskTables` | onResume / WiFi 导入后字库刷新 |

**两个需求的落点：**

- **开书探针回填不误删**：探针结果与存量参数一致时（`probed == effective`，`ReaderSettings` data class 全字段相等）提交本身就不发生，更谈不上清理；即使提交发生（如夜间切换、原书设置快照无变化），`cleanStaleDiskTables` 按指纹判定为空操作，当前参数下的有效磁盘表零误删。
- **字体修改必须删旧表**：换字体（族/字重进指纹）→ 指纹变 → 旧指纹表删除；字体集合变更（度量不进指纹）→ `cleanAllDiskTables` 全清兜底，B2 随后按当前指纹逐章重写。

未在单章写入后清理（`fullLayoutAndPersist` 落盘路径），避免破坏 B2 逐章后台计算；`PaginationCacheStore.cleanBookAll` 保留为全清入口。
