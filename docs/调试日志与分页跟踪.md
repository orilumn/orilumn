# 平板调试日志与分页跟踪查看指南

记录如何在平板（无线 adb）上找到调试日志、看懂分页跟踪输出，避免重启会话后重新摸索。

## 1. 连接平板（无线调试）

平板：vivo PA2353，内网 `172.16.0.203`，**端口号会变**（每次开无线调试都不同，例如 `172.16.0.203:45099`）。

```bash
adb connect 172.16.0.203:<当前端口>   # 从平板上「无线调试」界面抄当前端口
adb devices
```

注意：连接后 `adb devices` 可能同时出现**两个条目**（一个是 IP:端口，一个是 mDNS 的 `adb-400D91019H00000-...`），指向同一台平板。后续命令务必带 `-s` 指定：

```bash
adb -s 172.16.0.203:<端口> shell <命令>
```

端口变化后：`adb disconnect` 旧地址 → 重新 `adb connect`。其他工具（installDebug 等）默认选第一个设备即可，但批量调试命令建议统一用 `-s`。

## 2. 安装与启动

```bash
./gradlew :app:installDebug
adb -s 172.16.0.203:<端口> shell am start -n orilumn.reader/.MainActivity
```

- 包名 / applicationId：`orilumn.reader`
- 必须先启动（或任意一次布局/翻页）后，日志文件才会创建/追加。

## 3. 查看调试日志的两种方式

### 3.1 落盘文件（推荐，最全）

引擎日志（含分页跟踪）同时写进 app 私有目录，按天轮转（实际不一定是按天，随时有可能更新的）：

```
files/logs/日志_YYYYMMDD.txt        （当天）
files/logs/日志_YYYYMMDD.1.txt      （轮转出的旧文件）
```

读取（debug 版可用 run-as，无需 root）：

```bash
# 当天全部
adb -s 172.16.0.203:<端口> shell run-as orilumn.reader cat files/logs/日志_20260919.txt

# 只看分页跟踪
adb -s 172.16.0.203:<端口> shell run-as orilumn.reader cat files/logs/日志_20260919.txt | grep DBGPAGE

# 或顺带翻页/落位/布局上下文
... | grep -E "Orilumn.FLIP|PGAP|PGL|DISK-HIT"
```

日志行格式：`W 10:44:40.870 [Orilumn.DBGPAGE] 10:44:40.862 #[000785] <正文>`，`#[000NNN]` 是全局序号，方便跨 tag 按时间排序对照。

### 3.2 logcat（实时过滤）

```bash
adb -s 172.16.0.203:<端口> logcat -s Orilumn.DBGPAGE:W Orilumn.FLIP:W
```

> 注意：OEM（手上这台 vivo 就在列）会对 logcat 限流/丢行，实时看可以，**定论以 §3.1 落盘文件为准**
>（这就是落盘叫“最全”的原因；两边对不上时以文件为准）。

### 4.1 调度顺序标记（`Orilumn.Engine` / `Orilumn.SPIKE`）

调「谁先跑、谁抢谁」时按时间轴核这几条，它们就能还原整条派发链：

| 关键字 | 含义 |
|---|---|
| `b1 deferred by open gate ch=N` / `B2 deferred by open gate epoch=E` | 开书闸门压下了整章重排（总则 §第一优先级），只记账不派 |
| `open gate released ch=N b1=? b2=?` | 锚页排完、闸门开闩，被压下的整章重排在此补派 |
| `pg rolling ch=N page=P dir=D steps=S window=2` | 邻页全章预排**滚动派发**（同时最多 2 个，跑完一个补一个；`steps` 是本段序列长度） |
| `b1 dispatch ch=N prio=P headDist=d` / `b1 skip-fresh` | 本章全量 B1 的实际派发 / 跳过 |
| `whole-book B2 start epoch=E paramHash=H skipCh=C order=[…]` | 整书章扫描 B2 开始（`order` 是章距交错次序，前 8 个） |
| `spike-task start/done/cancel key=… prio=…` | 池里每个任务的起止（`Orilumn.SPIKE`）。滚动派发后 `pg:` 的 start/done 条数应 ≈ 在途数而非 `steps` |

### 4.2 `asm` 分段字段（`Orilumn.Engine`，每页排版一条）

| 字段 | 含义 |
|---|---|
| `shape=` | `tempShape` 窗口墙钟。**=` sBlk + sSkia + sStyles`（已完全归因）**，其中 `sBlk` 是块盒物化、非排版 |
| `sStyles=` / `sSkia=` | `shape` 段的真排版拆分：CSS 级联（`inlineStyles` 的 resolve 循环）/ Skia 断行（`shapeLeaf`）。**判断排版成本看这两个** |
| `sBlk=` / `sBlkF=` | `LightPrepare.block(i)` 物化总耗时 / 其中**第一次**的那笔。`sBlk≈sBlkF` 即"一次性初始化"而非逐块成本（曾据此定位 `computeFloatLeads` 的全章扫描 275ms） |
| `sBsty=` / `sBWid=` / `sBLft=` / `sBTxt=` | `sBlk` 的四段拆分：块样式 / 内容宽下降 / 内容左下降 / `textLength`。四段之和远小于 `sBlk` 时，差额在 `floatLeads[i]` 触发的 `floatData` 懒初始化里 |
| `sAdv=` | 曾是 `textLength` 里 `styledCharAdvance` 的耗时。R26 起该值改走 `globalCharStarts` 差分、不再现算，**故恒为 0ms**——它是"这条路没被走"的哨兵，一旦不为 0 说明有回退 |
| `cMatch=` / `cParse=` / `cBuild=` / `c2nd=` | `sStyles` 在渲染层内部的四段拆分：选择器匹配（`Cascade.winningDeclarations`）/ 内联 `style=""` 解析 / 建 `ComputedStyle`（`StyleComputer.computeStyle`）/ 通用字体名兜底的**二次**级联。**覆盖整个 shape 窗口内所有 `resolve`**（含 `blockStyleFor`），故可能略大于 `sStyles`。Rust 书实测 `cBuild` 占 ~75%——不是选择器慢，是构造 72 字段的值对象慢。⚠️ `c2nd` / `cParse` 在**本书**恒 0（该书无裸通用字体名、无内联 `style`），**这不是通用结论**：`c2nd` 非 0 意味着该章 CSS 命中了"级联重跑一遍"的字体兜底路径（级联成本翻倍），`cParse` 非 0 意味着有内联 `style=""` 要逐元素解析。换书时这两个字段**必须重新看**，不能拿本书的 0 推断该路径不需要 |
| `cEdge=` / `cFont=` | `cBuild` 的**第二层**拆分（R29）：`cEdge` = 「边」六兄弟（margin / padding / border-width / border-color / border-style / border-radius）合计，`cFont` = font-family 三连。⚠️ `cFont` 在 Rust 书只有 1~2ms（**不值得动**），但这不是通用结论——书里 CSS 简写越多、`cEdge`/`cFont` 占比越不同。拆出 `cEdge` 的结论见结论清单 §3b.5 |
| `eBox=` / `eWid=` / `eCol=` / `eSty=` / `eRad=` / `eBrd=` | `cEdge` 的**第三层**拆分（R29），边家族各计一笔：`eBox`=padding（margin 计入 `cEdge` 总量、未单列）/ `eWid`=`parseBorderEdges` / `eCol`=`parseBorderColors` / `eSty`=`parseBorderStyles` / `eRad`=`parseBorderRadius`；`eBrd` 是**计数不是耗时**——shape 窗口内真声明了 `border*` 属性的元素数。`eBrd` 用来分辨「空跑六个家族」与「真在解析」：`eBrd` 远小于 `sEls` 就说明绝大多数元素在无 border 声明的情况下白付了 `listOf(4)` + 字符串拼接查表（R39 即此情形，59/52）。⚠️ 换书必看，`eBrd≈sEls` 时本轮结论不适用 |
| `sBlocks=` / `sEls=` / `sDepth=` | 被塑块数 / 被 resolve 的元素数 / **被塑块最大嵌套深度**（GIMP ch18 报 624，Rust 报 2–3） |
| `warm=` / `warmB=` | 锚页前那笔预热的墙钟与块数。**`OPEN_WARMUP_BLOCKS` 已置 0，现恒为 0ms/0**，A/B 证明净亏（+50ms 开书）。留着字段只为日后试"更便宜的暖机" |
| `lines=` / `skia=` / `tbl=` / `box=` | 重建行流 / 投影 skia 窗 / 建表 / 装盒 |
| `pg=` 及其子段 | 分页段。`pgBackfill` 量的是「求 `prepare.totalChars` 实参 + `backfillBlockRanges` 本体」——**不是**纯函数耗时，见下 |
| `bf copy=… calc=… slices=… only=… blocks=…` | `backfillBlockRanges` 本体的两笔（列表拷贝 / 块范围计算）。**恒为 0ms**，是 `pgBackfill` 的护栏：它一旦不为 0 就是真出事了 |
| `pgHeap=` | **已删除**。该探针用 `Runtime.freeMemory()`，而 ART 实现是 `CollectGarbage(clear_soft_references=true)` 之后才返回——探针自己就是一次全量阻塞 GC，把平凡函数量成 1.3s。同理不要用 `Debug.threadCpuTimeNanos()`（vivo 实测首次 ≈1.2s、之后 ≈27ms） |

**`pgBackfill` 曾两次被误判**（都栽在探针上，详见 `docs/待分析-GIMP开书慢-结论清单.md` §2.1）：
一次判成 GC 停顿（实为探针自带的全量 GC），一次判成"线程在算"（实为 CPU 探针自身成本）。
真凶是实参 `LightPrepare.totalChars` 每次全章重算 CSS 级联 + 文本前进宽度测量，已修（§2.1）。

**`CascadeProbe.sink` 是全局可变量，已知保真度瑕疵。** 它挂在 shape 窗口上收集 `cMatch/cBuild` 等；
塑形全程在 `layoutMutex` 内单线程串行，但若真有第二个 layouter 实例同时 `resolve`，
它的时间会混进本笔账——**不崩，只是数不准**。要长期使用需按线程隔离。

## 5. `Orilumn.DBGPAGE` 分页跟踪字段（历史：只用于解读 R1 之前的旧日志）

> 本节已退役：源码入口曾是 `BodyPageView.setPage` → `BookDocumentController.debugCurrentPage`
>（旧路径 `app/src/main/java/com/orilumn/engine/BookDocumentController.kt` 文件末尾；现文件已迁
> `engine-skia/src/commonMain/kotlin/orilumn/reader/engine/BookDocumentController.kt:2362` 且零调用）。
> 当前替代：`Orilumn.FLIP` 的 `slice[firstLine,lastLine)char[charStart,charEnd)blk[blockStart,blockEnd)` 即当前页区间。

示例：

```
PAGE|ch=8 2 Kotlin mode=TEMP-INCR(锚点增量流)|slice char[9199,10158) line[1,31) blk[120,130)
|diskPages=46 diskPageIdx=12 rec=char[8575,9463)blk[113,123) !!MISMATCH-当前切片≠表页
 tempWin=fwd0/bwd2 cur=bwd[1] anchorBlk=165 shapedFwdTo=306 headReached=false headLanded=false
 pageNo=13/46 totalChars=37239
|content len=959 head=... ...tail=...|nextStart=...
```

| 字段 | 含义 |
|---|---|
| `mode=` | 当前页由哪个分页机制产出：<br>`TEMP-INCR(锚点增量流)` = 大章锚点临时 block-cut 分页（增量，盘表未用/未对齐）<br>`DISK-INCR(磁盘表+窗口增量成形)` = 命中磁盘表，只成形当前页所在窗口（增量）<br>`DISK-FULL(磁盘全量表)` = 磁盘 table 已绑定（全量）<br>`FULL-CHAPTER(全章布局)` = 整章布局（小章/遗留） |
| `slice char[a,b)` | 当前页可见字符区间（全章 char 流：`img`=1 槽，`br`=1） |
| `line[x,y)` / `blk[m,n)` | 页线区间 / 参与块区间 |
| `diskPages=N diskPageIdx=i rec=...` | 磁盘分页表规模、本页 char 在表中落在第 i 页、该页表记录区间 |
| `!!MISMATCH-当前切片≠表页` | 临时切片与磁盘表页区间**对不上**（增量与全量不一致的症状） |
| `tempWin=fwdA/bwdB cur=..` | 锚点流的窗口：前后页数、当前指针（`anchorBlk`=锚点块、`shapedFwdTo`=前向已成形块、`headReached/headLanded`=是否到章头） |
| `pageNo=13/46` | 相对章头的页码（章头=1）；盘表未落时分页号不可知 → `?(无盘表)` |
| `content len=N head=...tail=...` | 页内可见文本（显示首/尾 150 字，`[img]`=一张图、`\n`=换行）；`len` 是页真实长度 |
| `nextStart=...` | `charEnd` 之后 80 字的预览（= 下一页开头），用于核对接缝 |

## 6. 核对"当前页末尾 / 下一页开头"的流程（现行：基于 FLIP）

1. 连续翻两页，各抓一条 `Orilumn.FLIP`（`slice[行区间)char[字符区间)blk[块区间)` 即各页区间）。
2. 后页 `charStart` == 前页 `charEnd`（且行/块区间相接）即接缝连续；后页 `charStart` > 前页 `charEnd`，中间就是丢了内容——把两条 `#` 序号记下给开发。
3. 看 `inProgress=` / `diskTable=` / `layoutLC tempLC=` 判断当页走的是锚点临时流还是磁盘表/全量（对应 §7 的 MISMATCH 类症状）。
